## 19.1. Зачем это и почему сейчас

UV — это **фундамент**, на котором стоит всё остальное:

```
UV  →  атлас  →  текстура  →  бейкинг  →  экспорт в игру
```

Сейчас аддон умеет делать PBR-материал из папки с текстурами, но **не умеет
готовить саму текстуру**. Если UV кривые, то:

- текстура «мылится» в одном месте и чёткая в другом (разная плотность);
- при экспорте в игру атлас наезжает сам на себя (перекрытия);
- мипмапы тянут соседние острова в края (нет паддинга);
- перенести карту в **Krita** или **Aseprite** нечем — нет раскладки.

Твоя идея «быстро сделать хороший UV, а потом забрать карту в другую программу
и там дорисовать» — это ровно тот сценарий, который сейчас не закрыт вообще.

## 19.2. Что считать «хорошим UV»

Без критериев «хорошо» — пустое слово. Вот шесть, от важных к менее важным:

| # | Критерий | Что значит | Как проверяется |
|---|---|---|---|
| **1** | **Плотность текселей** (texel density) | одинаковое число пикселей на метр на всех объектах | тексели на метр = `пиксели / миры` по каждому острову |
| **2** | **Нет перекрытий** | два острова не занимают одно место | `uv.select_overlap` + свой анализ по bmesh |
| **3** | **Всё внутри [0,1]** | UV не вылезают за пределы картинки | свой анализ по bmesh |
| **4** | **Ровное искажение** | нет вытянутых треугольников | `uv.minimize_stretch` + метрика stretch |
| **5** | **Паддинг** | между островами есть зазор для мипмапов | свой «dilate» (в 5.x `uv.offset` **удалён**) |
| **6** | **Одинаковая ориентация** | острова не перепутаны повёрнутыми | доп. работа, опционально |

⚠️ **Критерий 1 — главный.** Молчаливый убийца качества: два объекта одного
размера, но один в сцене в 10 раз меньше другого, получат разную плотность
пикселей. Текстура на большем — мыльная, на маленьком — с шумом. **Именно
поэтому развёртка должна считаться в мировых единицах, а не «на глаз».**

## 19.3. Что Blender 5.2 реально умеет (проверено вызовом)

⚠️ Проверять надо **вызовом**: `hasattr(bpy.ops.uv, "что-то")` всегда вернёт
`True` (bpy создаёт операторы лениво), и отсутствующий оператор обнаружится
только при попытке вызова.

### Есть и работает (в Edit Mode, в том числе в `--background`)

| Оператор | Для чего |
|---|---|
| `uv.smart_project` | быстрая автоматическая развёртка (прямоугольные острова) |
| `uv.unwrap` | развёртка по швам (`ANGLE_BASED`, `CONFORMAL`) |
| `uv.pack_islands` | укладка островов в UV-пространство с зазором |
| **`uv.lightmap_pack`** | **атлас-пакер** с настройкой искажений — то, что нужно для игровых атласов |
| `uv.arrange_islands` | перестановка островов для уменьшения искажений |
| `uv.average_islands_scale` | выравнивание масштаба островов |
| `uv.minimize_stretch` | минимизация искажений |
| `uv.select_overlap` | подсветка перекрытий |
| `uv.mark_seam`, `uv.seams_from_islands`, `uv.rip`, `uv.stitch` | швы |
| `uv.export_layout` | **экспорт раскладки UV в PNG** (для внешних программ) |
| `uv.pin`, `uv.copy`, `uv.paste` | работа с UV вручную |

### **Удалено в 5.x** (было в 3.x/4.x)

| Оператор | Чем заменить |
|---|---|
| `uv.average_scale` | `uv.average_islands_scale` |
| `uv.offset` (паддинг) | **своя реализация на bmesh** |
| `uv.select_outside` | свой анализ по bmesh |
| `uv.transform`, `uv.stretch/scale/rotate` | `uv.align`, `uv.move_on_axis`, `uv.snap_cursor` |
| `uv.mark_sharp`, `uv.cut_seams_from_faces`, `uv.unite_faces` | `uv.seams_from_islands` + bmesh |

⚠️ **Это главный технический вывод разведки:** полагаться на хрупкие
операторы нельзя. Половина нужного в 4.x просто **исчезла** в 5.x, и половина
оставшегося требует контекста редактора и не работает в headless.

### Про контекст

- `uv.smart_project`, `uv.unwrap`, `uv.pack_islands` — работают **в 3D-вьюпорте**
  в Edit Mode, и в `--background` тоже ✓
- `uv.export_layout` — требует **живого Image Editor** в режиме UV; в
  `--background` падает ✗ → значит, его надо покрывать **в GUI**, а не
  headless-тестом
- `bpy.ops.image.external_edit` — открывает картинку во **внешнем редакторе**,
  путь к которому задаётся в `Preferences → File Paths → Image Editor`
  (`bpy.context.preferences.filepaths.image_editor`) ✓ — это и есть готовая
  точка входа для интеграции с Krita/Aseprite

## 19.4. Архитектурное решение: bmesh-first, операторы — вторым

Предлагаю строить UV-инструменты **на bmesh**, а операторы Blender
использовать только там, где они реально сильнее.

| | Операторы Blender | Свой код на bmesh |
|---|---|---|
| Тестируемость в headless | частично (контекст) | **полностью** |
| Устойчивость к версиям | ломается (5.x это уже показал) | **наша** |
| Контроль | «как получится» | **полный** |
| Скорость разработки | быстро | дольше |

**Что делается на bmesh** (наша territory): анализ островов, плотность
текселей, перекрытия, выход за [0,1], паддинг, отчёт.

**Что остаётся на операторах**: `unwrap` (наш собственный unwrapper — это
месяц работы, не разумно), `lightmap_pack` (атлас-пакер), `smart_project`.

## 19.5. Этапы работ

Каждый этап — законченный кусок с критерием «сделано» и тестом.

### Этап U1. Анализатор UV (только чтение) — ✅ сделано

**Цель:** увидеть, что не так, до того как что-то менять.

Что считаем по каждому острову (bmesh):

- bbox в UV и bbox в мировых координатах;
- **плотность текселей** = `sqrt(uv_area × пиксели_текстуры / world_area)`;
- площадь острова в UV и в мире → коэффициент искажения;
- перекрытия между островами;
- выход за [0,1];
- «шумные» острова (сильно вытянутые).

**Результат:** инструмент `uv.audit` + кнопка **«Проверить UV»** + отчёт в чат.

**Сделано, когда:** отчёт показывает плотность по каждому объекту и находит
перекрытие и выход за границы на заранее подготовленной сцене; всё это
проверяется headless-тестом.

**Размер:** M (2–4 дня)

⚠️ **Что вскрылось при реализации (три API-разрыва Blender 5.x):**

1. **`BMEdge.is_seam` переименован в `BMEdge.seam`.** Лемма: у ребра теперь
   `seam`, а не `is_seam`.
2. **`MeshLoop.vertex` удалён** — остался только `vertex_index`. Позиция вершины
   берётся через `mesh.vertices[loop.vertex_index].co`.
3. **`obj.matrix_world` устаревает**, пока не обновился depsgraph. Без
   `view_layer.update()` масштаб объекта не учитывается и плотность выходит
   неверной.

И ещё одно: **плотность не может существовать без размера текстуры.**
Анализатор берёт текстуру из Base Color материала объекта; если её нет —
говорит об этом отдельной находкой, а не выдумывает число.

Формула (проверена тестом до тысячных):

```
плотность = sqrt( (площадь_острова_в_UV × пиксели_текстуры) / площадь_острова_в_мире )
```

Площадь, а не bounding box: остров, лежащий по диагонали в UV, имеет большой
бокс и малую площадь.

### Этап U2. Развёртка: «быстро и хорошо» — ✅ сделано

**Цель:** одна кнопка даёт развёртку, которой не стыдно показать.

Конвейер:

```
1. поставить швы автоматически (по углу + по острым рёбрам)
2. uv.unwrap(method='ANGLE_BASED')
3. uv.minimize_stretch()
4. uv.pack_islands(margin=...)
```

**Швы автоматически** — на bmesh: ребро — шов, если угол между нормалями
соседних граней больше порога (по умолчанию ~40°) **или** ребро помечено
острым (`use_edge_sharp`). Это то, что делает развёртку «хорошей»: швы
идут по настоящим изломам, а не по случайным линиям.

**Результат:** кнопка **«Развернуть»** + инструмент `uv.unwrap` для модели.

**Сделано, когда:** кнопка на кубе/цилиндре даёт развёртку без перекрытий и с
одинаковой плотностью; есть кнопка отката одного шага.

**Размер:** M (2–4 дня)

#### Настройки — три уровня управления

| Уровень | Где | Что |
|---|---|---|
| **Проект** | свойства сцены (`gaa_uv_*`) + ползунок в панели AI | угол швов, метод, зазор, минимизация, острые рёбра, smart-fallback, плотность, размер атласа |
| **Вызов** | параметры инструмента | `uv.unwrap {"angle": 25, "margin": 0.01}` |
| **Ассистент** | снимок сцены | строка `UV settings: ...` — модель знает текущие числа |

⚠️ Настройки живут **в сцене**, а не в Preferences: у гейм-проекта и у
архвиз-проекта они разные, и переключать их руками перед каждым проектом —
лишнее.

#### Этап U2b. Развёртка по своим швам — ✅ сделано

Авто-швы по углу — это **потолок** возможностей. На персонаже, одежде и
механизмах нужно резать поверхность **там, где скажет художник**, а шов
должен идти **скрытым** (под воротником, по внутренней стороне руки).

Что сделано:

| Возможность | Как |
|---|---|
| **Развернуть только по своим швам** | галочка «Только по своим швам» в панели AI или `uv.unwrap {"own_seams": true}` — автоматические швы **не ставятся** |
| **Ручные швы не затираются** | `mark_seams` **только добавляет** швы, никогда не удаляет: решение художника — это решение |
| **Разрез по высоте** | `uv.mark_seams {"height": 1.2}` — меш **реально разрезается** на этой высоте (как `Ctrl+R`), и новые рёбра становятся швами. Рукава, сапоги, пояса |
| **Снять все швы** | `uv.mark_seams {"clear": true}` |
| **Находка «нет ни одного шва»** | замкнутая модель без швов развернётся одним куском — доктор об этом предупредит |

⚠️ **Техническая деталь про разрез по высоте.** Первый вариант искал рёбра, у
которых **оба конца** на нужной высоте. На кубе таких рёбер **нет**: они идут
от нижней грани к верхней. А нужный разрез проходит **сквозь** вертикальные
рёбра. Поэтому разрез делается через `bmesh.ops.bisect_plane` — он и создаёт
новое ребро вдоль линии разреза. Высота переводится в локальные координаты,
поэтому работает и для сдвинутого, и для масштабированного объекта.

#### Находки реализации

1. **Гладкие замкнутые поверхности не разворачиваются по углу.** У сферы нет
   рёбер с углом больше порога → швов ноль → `uv.unwrap` падает с «edge seams
   may need to be added». Решение: если швов не получилось и поверхность
   замкнута — **автоматическая развёртка** (`smart_project`), и в отчёте
   пишется, какой метод сработал.
2. **`BMEdge.is_seam` → `BMEdge.seam`** (см. этап U1).
3. **Операторы UV работают в `--background`** — проверено: `unwrap`,
   `minimize_stretch`, `pack_islands`, `lightmap_pack`, `smart_project` вызываются
   и в фоне, если объект активен и включён режим редактирования.

### Этап U2c. Симметричная развёртка — ✅ сделано

**Цель:** текстура вдвое меньше — рисуем половину, вторая получается зеркалом.

Классическая симметричная раскладка: **обе половины модели используют одну и ту
же область текстуры**. Рисуешь один раз — получаешь две стороны, а
эффективное разрешение **удваивается**.

Что сделано:

| Возможность | Как |
|---|---|
| **Отметить швы по плоскости симметрии** | `mark_symmetry_seams` — рёбра, лежащие на плоскости, становятся швами |
| **Посчитать UV для дальней половины** | `mirror_uvs` — UV второй половины копируются у соответствующих вершин |
| **Всё сразу** | `uv.symmetric` — швы + развёртка + зеркало |
| **Модель с модификатором Mirror** | аддон выключает «Mirror UVs» у модификатора: с ним текстура была бы **не** зеркальной |
| **Ось симметрии** | настройка сцены (X / Y / Z) + параметр на вызов |

⚠️ **Важно:** симметричная раскладка — это **перекрытие островов по
замыслу**. Такой объект нельзя класть в атлас: ему нужна **своя** текстура.

#### Три технические детали

1. **Плоскость симметрии задаётся в мире, а меши живут в локальных
   координатах.** Плоскость переводится обратной матрицей: нормаль — обратной
   транспонированной, точка — обратной. Так работает и для повёрнутого, и для
   масштабированного объекта.

2. **Соответствие вершин ищется по позиции.** У вершины и её зеркала одинаковое
   расстояние до плоскости. А вот **соответствие углов грани** ищется **по
   вершине, а не по порядку**: у зеркальной грани обратный порядок обхода.

3. ⚠️ **Четвёртый случай ловушки `is` против `!=`.** В bmesh при каждом
   обращении выдаётся **новая обёртка**, поэтому `other is not vert` всегда
   истинно — вершина «находит» саму себя. Нужно `other != vert`.

   И вторая ошибка в том же месте: индекс строился по **зеркальному** ключу, а
   поиск шёл по зеркальному же — вершина находила саму себя вместо
   counterparts. Индекс строится по **реальной** позиции, поиск — по зеркальной.

#### Проверено тестом

| Проверка | Результат |
|---|---|
| плоскость симметрии отмечена швами (8 рёбер) | ✓ |
| дальняя половина получила UV (12 углов) | ✓ |
| **соответствующие вершины делят UV** (4 пары) | ✓ |
| у модели с Mirror модификатором «Mirror UVs» выключен | ✓ |

### Этап U3. Плотность текселей (главный критерий) — ✅ сделано

**Цель:** одинаковая плотность пикселей на метр — на одном объекте и **между
объектами**.

Как считать:

```
плотность = sqrt( (площадь_острова_в_UV × пиксели_текстуры) / площадь_острова_в_мире )
```

Как чинить (на bmesh, без операторов): для каждого острова домножить
координаты UV на коэффициент `target / current` — вокруг центра острова.

Плюс **кросс-объектная** правка: взять плотность **эталонного** объекта и
привести к ней остальные.

**Результат:** кнопка **«Выровнять плотность»** + параметр «плотность в
пикселях на метр» в настройках аддона.

**Сделано, когда:** на трёх объектах разного размера после кнопки плотность
совпадает в пределах 1 %.

**Размер:** M (2–4 дня)

#### ⚠️ Главная тонкость: порядок операций

Плотность — **относительная** величина: упаковщик масштабирует все острова
**одним и тем же** коэффициентом, чтобы они влезли в текстуру. Значит, он
сохраняет **отношения** плотностей, но меняет абсолютное значение.

Отсюда порядок:

```
1. уложить острова            (pack_islands, scale=True)
2. измерить плотность каждого
3. домножить UV каждого острова на target / его_плотность
4. уложить острова СНОВА, но БЕЗ масштабирования (scale=False)
```

⚠️ **Шаг 4 — ключевой.** Обычная укладка (`scale=True`) снова растянула бы
острова по всей текстуре и **уничтожила** правку из шага 3. С `scale=False`
упаковщик только двигает острова, и плотность остаётся там, куда её поставили.

**Проверено тестом:** после правки разброс плотностей между островами — **1.000**
(то есть ровно), а абсолютное значение — 65.2 px/м при цели 64 (остаток 2 % от
финальной укладки).

#### Что ещё сделано в этом этапе

- **Новая находка**: «у объекта плотность островов разная: от X до Y px/м» —
  главный симптом «часть текстуры мыльная, часть резкая»;
- Кнопка **«Плотность»** и инструмент `uv.match_density` (с переопределением
  цели на вызов);
- Отчёт сообщает, **какой размер текстуры нужен**, чтобы острова поместились.

### Этап U4. Два режима финализации

**Цель:** из развёртки сделать **атлас** (режим A) или оставить **как есть**
(режим B). Ядро U1–U3 общее; здесь только финиш.

- Укладка с зазором: **своя** упаковка (упаковщик Blender работает только
  внутри одного объекта, а атлас — это **общая** текстура для нескольких).
- **Паддинг** (собственный, `uv.offset` в 5.x удалён): раздуть UV-острова на
  N пикселей. Реализация на bmesh: для каждого острова сдвинуть граничные
  UV-вершины наружу по нормали границы, с учётом того, что соседние острова
  не должны слипнуться.
- Генерация **пустой атласа** нужного размера (2048/4096) с белым фоном —
  основа для покраски.
- Отчёт: сколько места занято, сколько потеряно на зазоры, какой размер
  атласа нужен, чтобы влезть без сжатия.

**Результат:** кнопка **«Собрать атлас»** (создаёт/обновляет атлас-картинку) +
отчёт.

#### Как считается атлас

```
1. измерить остров каждого объекта
2. привести его к целевой плотности  →  UV-размер острова известен
3. уложить прямоугольники в атлас (полочный упаковщик)
4. записать координаты обратно в UV-слой каждого объекта
5. раздуть острова (паддинг)
```

⚠️ **Шаг 2 — то, что связывает атлас с плотностью.** Размер острова в атласе
определяется **мировым размером** и **плотностью**:
`размер = d · √(мировая площадь) / √(пиксели)`. Поэтому у всех объектов в
атласе одинаковая плотность **автоматически** — и атлас не может быть
«слишком плотным»: если суммарная площадь не влезает, инструмент сообщает,
какой размер текстуры нужен.

**Проверено тестом:** два куба → 12 островов в одном атласе, **разброс
плотности 1.000**, **ноль перекрытий**, всё внутри [0,1].

#### Паддинг: как раздуть остров

Граничные рёбра острова сдвигаются наружу по своей нормали. **Угловые вершины**
сдвигаются по биссектрисе — иначе угол получится тоньше остальных сторон.
Коэффициент: `1 / cos(половина угла между нормалями)`.

Для прямого участка (одно граничное ребро) сдвиг просто нормальный. Для
вырожденного угла (нормали погасили друг друга) берётся первая нормаль.

#### U4b. Режим B: своё — ✅ сделано

- Развёртка остаётся как есть: без укладки, без паддинга.
- Каждый остров — на своём месте; при желании 1:1 (без искажения).
- Отчёт: плотность по островам (своя у каждого) и площадь, которая понадобится
  при запекании.

**Результат:** инструмент `uv.unwrap_own` (тот же конвейер, но с выключенной
укладкой) + переключатель «Укладывать острова» в настройках сцены.

⚠️ U4b стоит почти ничего: это режим A **без двух шагов** (укладки и
паддинга) — потому что ядро U1–U3 общее. Именно это и было целью решения
«оба режима».

### Этап U5. Круговорот с другими программами

**Цель:** «сделал UV → забрал карту в Aseprite/Krita → дорисовал → вернул».

#### Что экспортируем («UV-комплект»)

```
wood_atlas/
    layout.png          ← раскладка UV (атлас, 2048×2048 по умолчанию)
    manifest.json       ← {atlas_size, margin, density, objects:[{name, islands, texture, albedo}]}
    albedo_Crate.png    ← копия текущей текстуры, если она есть
```

`manifest.json` — то, что делает комплект **самодостаточным**: размер атласа,
зазор, плотность, какие карты ожидаются. Без него через месяц никто не
вспомнит, какой размер был.

#### Как редактируют

- **Aseprite**: открыть `layout.png` как направляющий слой, рисовать атлас
  прямо по нему. (У Aseprite нет UV-фичи, но атлас — это просто картинка.)
- **Krita**: то же самое; у Krita есть фильтр «UV Map» для проверки.

#### Как возвращают

Кнопка **«Импорт атласа»**: выбрать PNG → он становится Base Color
материала активного объекта → UV не менялись → **атлас совпадает по построению**.

⚠️ Это ключевое свойство круговорота: раз пока UV не трогали, раскладка и
текстура совпадают всегда.

#### ⚠️ Почему раскладка рисуется нами, а не `uv.export_layout`

Оператор Blender `uv.export_layout` требует **живого** Image Editor — в
`--background` он падает. Инструмент, который работает только с открытой
мышью, невозможно покрыть тестами. Поэтому раскладка растеризуется здесь, на
данных bmesh: работает одинаково везде и покрыта headless-харнессом.

Растеризация — на numpy (он есть в Python Blender): треугольники островов
заливаются серым, границы — тёмной линией в 2 пикселя. Картинка имеет **тот
же размер, что атлас** и использует **то же пространство**, что UV, поэтому
пиксель картинки = пиксель текстуры.

**Результат:** кнопки **«UV-комплект»** и **«Импорт атласа»** + инструменты
`uv.export_kit` и `uv.import_atlas`.

**Сделано, когда:** экспорт даёт комплект, который открывается во внешней
программе, а импорт возвращает текстуру в материал без рассинхрона.

**Размер:** M (2–4 дня)

#### Что проверено

| Проверка | Результат |
|---|---|
| картинка раскладки не пустая, средний пиксель залит | ✓ |
| комплект на диске: layout.png + manifest.json + копия текстуры | ✓ |
| манифест описывает размер, плотность, зазор, острова и текстуры | ✓ |
| импорт кладёт картинку в Base Color | ✓ |
| **UV-координаты после импорта не изменились** | ✓ |
| импорт в материал без текстуры — создаёт узел сам | ✓ |

#### Как открыть во внешней программе (вне плана)

`bpy.ops.image.external_edit` открывает картинку в редакторе из
`Preferences → File Paths → Image Editor` — туда можно прописать Aseprite или
Krita. Отдельная кнопка не сделана: сначала нужно выгрузить комплект, а
дальше открыть `layout.png` обычным двойным кликом.

### Этап U6. Бейкинг — ✅ первая часть (B1–B2)

**Цель:** превратить процедурный материал в текстуры, которые понимает игровой
движок.

#### Что оказалось главным: не рендер, а подготовка

Запекание в Cycles — одна команда. А вот подготовить её — пять условий, и
нарушение **любого** даёт либо чёрную картинку, либо испорченную:

| Условие | Что будет, если нарушить |
|---|---|
| **движок Cycles** | EEVEE не умеет запекать вообще |
| **UV без перекрытий** | острова запекутся друг в друга |
| **изображение-таргет** | некуда писать |
| **узел-таргет: активный И выделенный** | «No active and selected image texture node found» |
| **цветовое пространство и float buffer** | карта нормалей保存 как цвет → мусор |

#### ⚠️ Три открытия при реализации

1. **`other is node` — всегда False** для структур bpy (каждый доступ выдаёт
   новую обёртку). Из-за этого узел-таргет **не был выделен**, и запекание
   молча отменялось. Правильно — `other == node`.
2. **Сообщение об ошибке не говорит, какой узел имелся в виду.** Формулировка
   «No active and selected image texture node found in material» звучит как
   «в материале нет узла», а на самом деле узел есть — просто не выделен.
3. **Кубик из стартовой сцены съедает лучи.** Если в сцене есть другой меш в
   той же точке, запечённого куба не видно: bake лучи упираются в чужой
   объект. В тесте кубик из сцены удаляется.

#### Что сделано (B1–B2)

**`baking.py`**:

- `check_ready(obj)` — проверки готовности: есть UV, нет перекрытий, есть
  материал, есть источник высоты (иначе нормали плоские), движок умеет
  запекать;
- `bake(obj, targets, size, margin, samples, save_to)` — создаёт таргеты,
  переключает движок на Cycles, печёт, **убирает за собой** (временные узлы
  удаляются, картинки остаются в файле), восстанавливает движок и число
  сэмплов, пишет файлы на диск по запросу;
- инструменты `bake.maps` и `bake.check`, кнопка **«Запечь»**.

Типы карт: albedo, diffuse, normal, roughness, ao, shadow, emission. Для
карт данных автоматически ставятся `Non-Color` и float buffer.

**Проверено тестом:**

| Проверка | Результат |
|---|---|
| объект без UV / без материала / без источника высоты — найдены | ✓ |
| запекание albedo и normal | ✓ |
| движок восстановлен после запекания | ✓ |
| временные узлы удалены, картинки остались | ✓ |
| albedo — цвет (sRGB), normal — данные (Non-Color + float) | ✓ |
| **карта нормалей указывает вверх (0.5, 0.5, 1.0)** | ✓ |
| PNG действительно на диске | ✓ |

⚠️ Бейкинг занимает **главный поток**: на большой сцене Blender «зависнет» на
минуты. Это нормально для запекания, но пользователь должен знать заранее.

#### Что дальше (B3–B5)

| Этап | Что | Размер | Статус |
|---|---|---|---|
| **B3** | Нормали из карты высот (дифференцирование) — аналог xNormal | M | ✅ сделано |
| **B4** | Запекание нескольких объектов в один атлас + проверка, что паддинга хватает | M | ✅ сделано |
| **B5** | Автозамена процедурного материала на запечённые текстуры | M | ✅ сделано |

#### Этап B4: несколько объектов в один атлас — ✅ сделано

⚠️ **Открытие реализации.** Blender запекает **каждый выделенный объект в
таргет СВОЕГО материала**. Чтобы несколько объектов попали в **одну**
картинку, у каждого должен быть свой узел-таргет, и все они должны указывать
на **одно и то же** изображение. Забытый объект → отмена запекания с
«No active and selected image texture node found in material "CubeB_mat"».

**Проверка паддинга.** Зазор между островами в пикселях (`зазор × размер
атласа`) сравнивается с паддингом запекания: если зазор меньше, острова
**затекут** друг в друга. Инструмент предупредит до запекания.

**B5: замена материала.** Собирается новый обычный материал из запечённых
текстур (albedo → Base Color, normal → **через узел Normal Map**, roughness →
Roughness) и ставится на объект. Процедурный материал **остаётся в файле** —
ничего не удаляется.

#### Этап B3: нормали из карты высот — ✅ сделано

**`heightmap.py`**: карта высот превращается в карту нормалей через
**производную**.

```
n = normalize( (-dh/du * strength, -dh/dv * strength, 1) )
rgb = n * 0.5 + 0.5
```

Ровно то, что делают xNormal и Substance, но не выходя из Blender.

⚠️ **Два решения, которые стоит знать:**

1. **Производная берётся на единицу UV, а не на пиксель.** Иначе результат
   зависит от разрешения карты высот: одна и та же лепка, выгруженная в 2K и
   в 4K, дала бы разный рельеф. Проверено тестом: рамп 64 px и рамп 256 px
   дают **одинаковую** нормаль (0.146 против 0.146).
2. **Зелёный канал — по конвенции OpenGL** (+Y вверх), как у нормалей Blender
   и большинства игровых движков. `flip_y` переключает на DirectX.

Результат — **карта данных**: `Non-Color` и float buffer. Сохранённая как
sRGB, карта нормалей теряет смысл при смене цветового пространства.

**Проверено тестом:**

| Проверка | Результат |
|---|---|
| плоская карта высот → плоская нормаль (0.5, 0.5, 1.0) | ✓ |
| рамп вверх → нормаль наклоняется к **-u** | ✓ |
| результат **не зависит от разрешения** | ✓ |
| сила увеличивает наклон | ✓ |
| `flip_y` меняет только зелёный канал | ✓ |
| float buffer + Non-Color | ✓ |
| карта нормалей подключается во вход Normal материала | ✓ |

## 19.7. Открытые вопросы — нужно твоё решение

### В1. Профиль UV: гейм-атлас или развёртка «по швам»?

> **✅ РЕШЕНО: оба режима, постепенно.**
>
> Инструмент должен уметь и атлас для игр, и «свободную» развёртку для всего
> остального (архвиз, запекание, 3D-печать, фотограмметрия).
>
> Ключевое наблюдение, которое делает это возможным без удвоения работы:
> **ядро у режимов общее**. Анализ, швы, развёртка и плотность работают
> одинаково. Различается **только финальная укладка**:
>
> | | Режим A: атлас | Режим B: своё |
> |---|---|---|
> | укладка `pack_islands` | **да** | **нет** |
> | паддинг | **да** | нет |
> | атлас-картинка | **да** | нет |
> | плотность | общая на весь атлас | своя у острова (часто 1:1) |
>
> Поэтому порядок такой: **сначала ядро (U1–U3), потом два «финиша» (U4a и
> U4b)**. Режим B — это, по сути, режим A без двух шагов, поэтому он почти
> бесплатен.

### В2. Насколько «умной» должна быть развёртка?

> **✅ РЕШЕНО: вариант A** — авто-швы по углу (40°) + острые рёбра →
> `uv.unwrap(ANGLE_BASED)` → `uv.minimize_stretch()` → `uv.lightmap_pack()`.
> Надёжно, предсказуемо, покрыто тестами.

### В3. Что считать «эталонной плотностью»?

> **✅ РЕШЕНО: вариант A** — плотность в **пикселях на метр** (настройка аддона,
> например «16 px/м»). Цифра, понятная всем, одинаковая для всех объектов сцены.

### В4. Насколько глубоко делать круговорот с внешними программами?

> **✅ РЕШЕНО: вариант B** — комплект (раскладка + текстуры + манифест) +
> кнопка открытия во внешнем редакторе (`image.external_edit`).
> Автоматический возврат (вариант C) — отдельная задача, если понадобится.

### В5. Нужны ли слои островов в одном PSD?

> **✅ РЕШЕНО: вариант A** — нет. Плоский атлас PNG покрывает Aseprite и
> Krita. PSD-слои по островам — отдельная большая реализация, в план не входит.

### В6. Тестируемость: насколько глубоко копать в bmesh?

> **✅ РЕШЕНО: вариант B** — всё критичное на bmesh (анализ, плотность,
> паддинг), операторы только там, где они сильнее (`unwrap`, `lightmap_pack`,
> `smart_project`). Так всё покрыто headless-тестами и не ломается при смене
> версии Blender.

- **Текстурная живопись в самом Blender** (Texture Paint) — не наша задача,
  мы делаем путь «вне Blender».
- **Генерация карт нормалей** — в У6.

## 19.10. Итог главы

- UV — это фундамент для атласа, текстуры, бейкинга и экспорта; сейчас аддон
  не умеет ничего из этого.
- «Хороший UV» = 6 критериев, из которых главный — **плотность текселей**.
- Blender 5.2 **потерял** половину нужных UV-операторов (`uv.offset`,
  `uv.average_scale`, `uv.select_outside`), а `uv.export_layout` требует
  живого UI — отсюда решение **строить своё на bmesh**, а на операторы
  полагаться только там, где они сильнее.
- Проверено и доступно: `unwrap`, `smart_project`, `pack_islands`,
  **`lightmap_pack`** (атлас-пакер), `minimize_stretch`,
  `average_islands_scale`, `export_layout`, `image.external_edit`.
- Круговорот с Krita/Aseprite держится на простом свойстве: **пока UV не
  менялись, раскладка и текстура совпадают всегда**.
- Шесть открытых вопросов (19.7) — твои решения, без них не начинаем.
