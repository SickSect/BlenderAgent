# Глава 4. Выполнение AI-кода: `exec`, контекст и разбор краша

Вот здесь живёт самая рискованная функциональность аддона — кнопка «Выполнить код».
Она берёт Python-код из ответа модели и выполняет его **внутри Blender**, в текущей
сцене. Эта глава объясняет, как это устроено шаг за шагом, и разбирает аварию, которую
мы поймали и починили: падение Blender после выполнения скрипта.

## 4.1 Как код попадает из ответа в кнопку

Модель оформляет код в так называемые **fenced code blocks** (ограждённые блоки):

````
Вот скрипт:

```python
import bpy
bpy.ops.mesh.primitive_cube_add(size=2)
```

Он добавит куб.
````

Аддон вылавливает **последний** такой блок. Ищет его регулярным выражением
📦 `state.py`:

```python
_CODE_BLOCK_RE = re.compile(r"```([A-Za-z0-9_+-]*)[ \t]*\n(.*?)```", re.DOTALL)
_CODE_LANGS = ("", "python", "py", "bpy")

def extract_last_code(text: str) -> str:
    last = ""
    for lang, body in _CODE_BLOCK_RE.findall(text or ""):
        if lang.lower() in _CODE_LANGS:
            last = body
    return last.strip("\n")
```

Разберём регулярное выражение по кусочкам:

| Часть | Смысл |
|---|---|
| `` ``` `` | три обратных кавычки — открытие блока |
| `([A-Za-z0-9_+-]*)` | группа 1: язык после открытия (`python`, `py`, `` пусто `` …) |
| `[ \t]*\n` | до конца строки с открытием |
| `(.*?)` | группа 2: **тело кода**; `?` — «жадность выключена», берём до первого закрытия |
| `` ``` `` | три обратных кавычки — закрытие |
| `re.DOTALL` | чтобы `.` совпадал и с переводами строк |

`findall` возвращает **все** блоки; цикл оставляет последний подходящий (по языку).
Почему «последний»? Потому что в ответе обычно сначала идут пояснения/примеры, а
готовый рабочий скрипт — в конце.

⚠️ `_CODE_LANGS` включает пустую строку: некоторые модели открывают блок без
указания языка (просто три обратные кавычки). Мы это принимаем.

Дальше по цепочке (📦 `state.py:_handle`) при событии `done`:

```python
self.pending_code = extract_last_code(self.stream_buf)
self.code_ran = False
```

- `pending_code` — «код, предложенный к запуску»;
- `code_ran` — «этот блок уже запускали». Обнуляется только при новом ответе.

Именно `code_ran` рисует вместо кнопки надпись «Выполнен · Ctrl+Z — отмена»
(📦 `ui.py`). Это первая линия защиты: **один блок — один запуск**.

## 4.2 `exec`: что это вообще такое

`exec` — встроенная функция Python, которая выполняет **строку как программу**:

```python
exec("x = 2 + 2")
print(x)        # 4
```

Три ключевых факта:

1. `exec` выполняется **в том же процессе и потоке** — здесь, в Blender.
2. Переменные попадают в **словарь-пространство имён**, который ты передаёшь.
3. `exec` **ничего не возвращает** и не ловит исключения — их ловить нужно самому.

📦 `operators.py:GAA_OT_run_code.execute`:

```python
namespace = {"bpy": bpy, "__name__": "__gaa_ai__"}
_exec_script(code, namespace, stdout, context)
```

Почему `bpy` «заранее положен» в namespace? Чтобы код модели с `import bpy` и без
него одинаково работал: даже если модель забудет импорт, `bpy` уже виден.

Почему `__name__ = "__gaa_ai__"`, а не `"__main__"`? Потому что часть скриптов
оформляют точку входа так:

```python
if __name__ == "__main__":
    main()
```

Если бы мы подставили `"__main__"`, этот блок **неожиданно запустился бы**. А с
произвольным именем — не запустится, и код остаётся «библиотечным».

### Один namespace или два?

`exec(code, globals, locals)` может принимать два словаря. Мы передаём **один**, и это
осознанно: тогда глобальные и локальные имена — одно и то же, и функции, определённые
внутри скрипта, видят друг друга и переменные верхнего уровня. С двумя словарями код
модели ломался бы на ровном месте.

### Скомпилированный код и имя файла

Внутри `_run_in_context` (📦 `operators.py`):

```python
exec(compile(code, "<AI Assistant>", "exec"), namespace)
```

`compile` делает из строки объект «код» **заранее**, а вторым аргументом задаёт
«имя файла». Оно появится в traceback, и вместо безымянного `<string>` ты увидишь
удобное `<AI Assistant>`. Мелочь, но заметно улучшает читаемость ошибок.

## 4.3 Ловим `print()` и ошибки

Скрипт модели может печатать в консоль. Показывать это пользователю в чате удобнее,
чем в системной консоли. Для этого стандартный вывод временно подменяется на
строковый буфер (📦 `operators.py`):

```python
import io
from contextlib import redirect_stdout

stdout = io.StringIO()
try:
    _exec_script(code, namespace, stdout, context)
except Exception:
    state.add_display("error", i18n.T("msg.code_error") + "\n" + traceback.format_exc())
else:
    message = i18n.T("msg.code_done")
    printed = stdout.getvalue().strip()
    if printed:
        message += "\n\n" + i18n.T("msg.output") + "\n" + printed
    state.add_display("result", message)
```

`redirect_stdout(stdout)` — это **менеджер контекста** (внутри `_exec_script`): всё, что
код печатает, попадает в `StringIO`, а после выхода из блока вывод возвращается на
место. Это стандартный приём «перехватить print».

Ошибки: любой `Exception` ловится и показывается как `traceback.format_exc()` —
полная трассировка из `<AI Assistant>`. Пользователь сразу видит строку и причину.

## 4.4 Контекст: почему `bpy.ops` «не любит» чужие окна

Это ядро проблемы краша. Вспомним из главы 1: `bpy.ops.*` **контекстно-зависимы**.

Кнопка «Выполнить код» нажимается из **popup-окна** или **боковой панели**. Значит,
в момент вызова:

- `context.area` — что угодно (N-панель, popup), но **не 3D-вьюпорт**;
- `context.region` — `UI`-регион, а не `WINDOW`-регион вьюпорта.

А код модели может содержать `bpy.ops.object.duplicate()`, `bpy.ops.object.join()`,
`bpy.ops.object.delete()` и т.п. Эти операторы рассчитаны на вызов из вьюпорта и в
«неправильном» контексте идут по другому пути исполнения.

📦 Решение — `operators.py:_exec_context`: собрать правильные переопределения
контекста.

```python
def _exec_context(context) -> dict:
    overrides = {}
    window = getattr(context, "window", None)
    if window is not None:
        overrides["window"] = window

    screen = getattr(context, "screen", None) or getattr(window, "screen", None)
    area = region = None
    if screen is not None:
        overrides["screen"] = screen
        for candidate in screen.areas:            # ищем настоящий 3D-вьюпорт
            if candidate.type == "VIEW_3D":
                area = candidate
                for reg in candidate.regions:
                    if reg.type == "WINDOW":
                        region = reg
                        break
                break
    if area is not None:
        overrides["area"] = area
        space = area.spaces.active
        if space is not None:
            overrides["space_data"] = space
        if region is not None:
            overrides["region"] = region
    if getattr(context, "scene", None) is not None:
        overrides["scene"] = context.scene
    if getattr(context, "view_layer", None) is not None:
        overrides["view_layer"] = context.view_layer
    return overrides
```

Что здесь важно:

- Мы **не выдумываем** контекст, а берём настоящие объекты Blender: настоящее окно,
  настоящий экран, **настоящий 3D-вьюпорт** (`area.type == "VIEW_3D"`) и его
  `WINDOW`-регион.
- `space_data = area.spaces.active` — данные самого 3D-вьюпорта.
- `view_layer` и `scene` переносим как есть — операторам нужен корректный слой
  видимости.

И применяем это через `temp_override` (📦 `_exec_script`):

```python
overrides = _exec_context(context)
with redirect_stdout(stdout):
    if overrides and hasattr(bpy.context, "temp_override"):
        with bpy.context.temp_override(**overrides):
            _run_in_context(code, namespace)
    else:
        _run_in_context(code, namespace)
```

`hasattr(..., "temp_override")` — проверка на старые версии Blender (< 3.2), где
`temp_override` ещё не было. Тогда просто выполняем как есть.

## 4.5 Депграф: что «пересчитывает» Blender

Чтобы понять краш, придётся понять **dependency graph (депграф)**.

Blender не хранит «готовую картинку» сцены. Он хранит **зависимости**: объект зависит
от своего меша, материалы — от нод, модификаторы — от исходной геометрии и т.д. Перед
отрисовкой Blender проходит этот граф и **вычисляет** актуальное состояние. Это
называется «rebuild depsgraph».

Когда ты меняешь сцену через Python, депграф помечается «грязным» и пересчитывается
не сразу, а в удобный момент — обычно в **цикле событий** (`wm_event_do_depsgraph`,
перед отрисовкой кадра).

Отсюда — обычная строка:

```python
bpy.context.view_layer.update()
```

Она говорит: «пересчитай состояние **прямо сейчас**». Мы делаем это сразу после
выполнения скрипта (📦 `_run_in_context`), пока валидный контекст ещё активен:

```python
def _run_in_context(code: str, namespace: dict) -> None:
    exec(compile(code, "<AI Assistant>", "exec"), namespace)
    try:
        bpy.context.view_layer.update()   # «осесть» здесь, а не в цикле событий
    except Exception:
        pass
```

## 4.6 Разбор аварии: что именно упало

### Симптом

Blender **аварийно закрывался** после выполнения AI-кода. Причём не во время скрипта —
а чуть позже, когда пользователь уже ничего не делал.

### Что показал отчёт о падении

- Тип: `EXCEPTION_ACCESS_VIOLATION (0xc0000005)`, чтение по адресу `0x0`
  (нулевой указатель).
- Самая верхняя (внешняя) часть C-стека:

  ```
  blender::deg::DepsgraphNodeBuilder::build_materials
      ← build_object_data
      ← ... (внутренние вызовы депграфа) ...
      ← wm_event_do_depsgraph
  ```

- При этом секция `# Python backtrace` **пустая**.

Три вывода, которые из этого следуют:

1. **Падение не в Python.** Если бы падал наш `exec`, в отчёте был бы Python-traceback.
   Пусто → код Python отработал нормально, а упал C++ уже **после** него.
2. **Падает пересчёт депграфа.** `build_materials` — это фаза построения «материалов»
   в графе зависимостей. Значит, беда в данных сцены/связях материалов, а не в логике
   скрипта.
3. **Момент падения — цикл событий** (`wm_event_do_depsgraph`), то есть отложенный
   пересчёт, который Blender делает сам перед отрисовкой.

### Причинная цепочка

Собрав данные из логов (`%TEMP%\gaa_*\events.jsonl` и `worker.log`), мы увидели:

1. В сцене выполнялся код с `bpy.ops.object.duplicate()`.
2. Кнопку «Выполнить код» нажимали **несколько раз** — код с дублированием
   выполнялся повторно.
3. Оператор дублирования вызывался из контекста **popup/боковой панели**, а не из
   3D-вьюпорта.

Итог: депграф оставался в неконсистентном состоянии (дубликаты со ссылками на данные,
созданные в «неправильном» контексте), а когда цикл событий запускал полный пересчёт —
в `build_materials` происходило разыменование `nullptr`.

### Как подтверждали гипотезу

- **Стресс-тест**: скрипт, делающий 60 дублирований **в нормальном контексте** (из
  скрипта в 3D-вьюпорте) — краша нет. Значит, дело не в самом дублировании, а в
  контексте и/или повторах.
- **Проверка «одного запуска»**: после правок повторное нажатие стало невозможным
  (`poll()` возвращает `False`), а первый запуск работает штатно.

### Что изменили (и почему помогает каждое)

| Изменение | Зачем |
|---|---|
| Выполнение в `temp_override` с настоящим 3D-вьюпортом (`window/screen/area/region/space_data`) | операторы идут «штатным» путём, депграф не оставляется в кривом состоянии |
| `view_layer.update()` сразу после `exec` | пересчёт происходит здесь и сейчас, а не откладывается в цикл событий |
| `bl_options = {"REGISTER", "UNDO"}` | весь скрипт — один шаг `Ctrl+Z`; пользователь может откатить |
- **Одноразовый запуск** (`poll` запрещает повтор, `code_ran`) | нельзя случайно выполнить один и тот же скрипт дважды и накопить дубликаты
- **Метка «Выполнен»** вместо кнопки — визуальная обратная связь

### Честная оговорка

Мы устранили **триггер** (конкретную комбинацию «оператор + плохой контекст +
повторы»), но это выглядит как **баг самого Blender** в фазе `build_materials`
(разыменование `nullptr` при определённых связях). Полностью исключить падение на
любом коде мы не можем. Поэтому:

> ⚠️ **Перед запуском AI-кода сохраняй .blend-файл** (`Ctrl+S`). Если Blender всё же
> упадёт — открой свежий отчёт о падении (`%TEMP%\Blender.crash.txt`) и заведи тикет в
> трекер Blender. Так баг в Blender поймают и починят.

### Что мы поменяли в коде — сводка

| Симптом | Причина | Исправление |
|---|---|---|
| Падение в `build_materials` | пересчёт депграфа в плохом состоянии | `view_layer.update()` сразу после скрипта |
| Неверное поведение операторов | контекст popup/панели | `_exec_context()` + `temp_override` |
| «Взрыв» сцены при повторном клике | повторный запуск того же кода | one-shot `poll` + `code_ran` |
| Невозможно откатить | изменения не в одной транзакции | `bl_options = {"REGISTER", "UNDO"}` |

## 4.7 Правила безопасности (запомнить)

1. **Сохраняй файл** перед запуском AI-кода (`Ctrl+S`).
2. **Читай код перед запуском.** Ты — последняя инстанция; выполняешь именно ты.
3. **Один блок — один запуск.** Кнопка исчезает после выполнения — это не баг, это
   защита. Хочешь ещё раз — попроси модель прислать блок заново.
4. **`Ctrl+Z` откатывает весь скрипт** одним шагом.
5. Если что-то пошло не так — смотри сообщение «Код»/«Ошибка» в чате, там traceback.

## 4.8 Что попробовать руками

1. **Проверить одиночный запуск.** Попроси модель добавить куб, нажми «Выполнить код»,
   затем попробуй нажать ещё раз — кнопки уже нет, вместо неё «Выполнен».
2. **Проверить Undo.** После запуска нажми `Ctrl+Z` — куб должен исчезнуть (весь
   скрипт — один шаг).
3. **Поймать вывод.** Попроси код с `print("привет")` — в чате появится блок «Вывод:».
4. **Поймать ошибку.** Запусти заведомо сломанный код (`bpy.ops.object.join()` без
   выделения) — в чате появится traceback, Blender не закроется.

## 4.9 Итог главы

- Код модели извлекается регуляркой, только последний fenced-блок.
- `exec` выполняется в одном namespace с уже доступным `bpy`; вывод перехватывается
  в `StringIO`, ошибки — в traceback.
- Операторы требуют правильного контекста, поэтому мы подставляем настоящий
  3D-вьюпорт через `temp_override`.
- Депграф «оседает» немедленно через `view_layer.update()`.
- Краш был в C++-пересчёте депграфа, а не в Python; мы убрали триггер
  (контекст + повторы) и добавили Undo и one-shot.
- **Сохраняй файл и читай код** — это правило никуда не ушло.
