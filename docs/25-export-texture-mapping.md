# Глава 25. Как маппинг из Blender доезжает до игры

> 📦 `src/blender_addon/uvmapping.py` (перенос маппинга в UV),
> `src/blender_addon/export.py` (экспорт, вызывает перенос и откатывает его),
> `tests/run_uvmapping_check.py`.
>
> ⚠️ Глава про **устройство**, а не про кнопку. Кнопка «Экспорт» уже всё делает
> сама; здесь объяснено, почему без этого шага картинка в игре выглядит иначе.

---

## 25.1. Проблема одним предложением

В Blender текстуру можно **сдвинуть, повернуть и повторить** нодой `Mapping`, а
координаты для неё взять не из UV, а из геометрии объекта. Экспорт в игру эти
ноды **не переносит**: в файле остаётся только картинка и UV. Поэтому в игре
текстура ложится по-другому.

Пример из `E:\ASSETS\Walls.blend`, материал `Wallpaper`:

```
Texture Coordinate (Object) → Mapping (Texture, scale 3×2, rot 60°/90°) → Image Texture → Base Color
```

Координаты взяты из **объекта**, а не из UV. Движок такой цепочки не знает и
берёт UV — отсюда расхождение.

---

## 25.2. Что принимает, во что преобразует, кому отдаёт

```
вход:   материал с цепочкой  Texture Coordinate → (Mapping)* → Image Texture
        (*) сколько угодно Mapping с константными входами
преобразует: цепочку считает для каждого угла (loop) каждой грани
        и пишет результат в ОДИН UV-слой объекта: GAA_EXPORT
выход:  файл GLB / FBX, где у каждой текстуры одна UV-карта,
        и сцена, которая после экспорта возвращается как была
```

Почему это возможно без запекания: маппинг — **аффинное** преобразование
(сдвиг, поворот, масштаб). Координата линейна по позиции вершины, а UV
интерполируется линейно. Значит, перенос цепочки в UV даёт **тот же результат
по всей грани**, без потери разрешения и без времени на запекание. Тайлинг
сохраняется, потому что UV могут выходить за пределы 0..1.

---

## 25.3. Математика Mapping-ноды

У ноды три входа: `Location` (сдвиг), `Rotation` (углы Эйлера, порядок XYZ),
`Scale`. У неё есть режим `Vector Type`, и от него зависит формула.

| Режим | Формула | Комментарий |
|---|---|---|
| `POINT` | `T · R · S · v` | прямое преобразование, сдвиг учитывается |
| `TEXTURE` | `(T · R · S)⁻¹ · v` | **обратное** — так работает пространство текстуры |
| `VECTOR` | `R · S · v` | сдвиг не учитывается |
| `NORMAL` | — | не точка, в UV не переносится, пропускается |

Режим по умолчанию — `POINT`, а у `Walls.blend` стоит **`TEXTURE`**. Именно
поэтому нельзя просто переложить `T·R·S`: получился бы другой результат.

Как это проверено. Мы запекли результат ноды в картинку и сравнили пиксели с
формулой (1 пиксель = 1/64, ошибка 1e-5 — это округление пикселя):

```
POINT   rot=(1.0472, 0, 1.5708)  ошибка 0.00005
POINT   rot=(0.5, 0.3, 0.2)      ошибка 0.00009   ← все три оси, порядок XYZ верен
TEXTURE rot=(1.0472, 0, 1.5708)  ошибка 0.00001
TEXTURE rot=(0.5, 0.3, 0.2)      ошибка 0.00001
```

## 25.4. Почему один слой на объект, а не по слою на материал

Здесь есть ловушка, и она стоила двух попыток.

**FBX не умеет выбрать UV-карту для текстуры.** В экспортере Blender есть поле
`UVSet`, но в коде оно жёстко задано пустым (`uvset = None`, файл
`io_scene_fbx/export_fbx_bin.py`). Значит, движок читает **первую** UV-карту
объекта — какой бы материал ни ссылался на вторую.

Поэтому:

* один слой на материал **не работает** для FBX: второй слой есть, но текстура
  всё равно читает первый;
* один слой на **объект** работает: в нём для каждой грани записаны UV того
  материала, которому грань принадлежит. Грань с `Wallpaper` получает
  пересчитанные координаты, грань с `Wood_Dark_Bake` — свои исходные. Каждая
  грань использует только свою текстуру, поэтому одной картой обходятся все.

```
грань 0..2  (Wallpaper)      → UV = (T·R·S)⁻¹ · координата_объекта
грань 3..5  (Wood_Dark_Bake) → UV = исходная UV-карта
              ↓
объект: один слой GAA_EXPORT → FBX и GLB читают его
```

Проверено на `Walls.blend`: после переноса у `WallDoor` и `WallWindow` остаётся
один UV-слой `GAA_EXPORT`, материалы ссылаются на него, в GLB у всех примитивов
только `TEXCOORD_0`.

## 25.5. Что переносится, а что нет

| Случай | Что делаем |
|---|---|
| `Texture Coordinate` (UV / Object / Generated) → один или несколько `Mapping` | переносим |
| `UV Map` нода с именем UV-слоя → `Mapping` | переносим |
| Текстура без Vector-входа | ничего не делаем, движок берёт активный UV |
| Разные цепочки в **одном** материале (например, базовая карта с Object, нормаль с UV) | **не переносим**: на одну грань нужны два разных UV — это запекание |
| `NORMAL` координаты, `Box`/`Sphere` проекция, математика между координатой и картинкой | **не переносим**, сообщаем |
| Ноды цвета между картинкой и BSDF (Mix, ColorRamp, HSV) | не переносятся вообще — нужен бейк (глава 21) |

Что **не** пропускается молча: каждый отказ попадает в отчёт экспорта с
причиной. Например:

```
Moved texture mapping into UVs for the export: Wallpaper -> GAA_EXPORT
Texture mapping that still needs a bake:
- Mixed: its maps use different coordinate chains (one UV set cannot serve them)
```

## 25.6. Как не испортить .blend

Экспорт **временно** меняет сцену и сразу возвращает её:

1. запоминаем UV-слои объекта (данные, какой активный);
2. считаем цепочки и пишем `GAA_EXPORT`;
3. переподключаем ноды материалов на `UV Map` с этим именем;
4. удаляем остальные UV-слои (чтобы FBX увидел только наш);
5. экспортируем;
6. **в `finally`** удаляем `UV Map`-ноды, возвращаем связи, восстанавливаем UV-слои
   и активный слой.

Проверено: после экспорта `WallDoor` снова имеет `UVMap`, а `Wallpaper` снова
подключён через `Mapping`. Тест `part_export` проверяет именно это.

Два правила, которые соблюдаются ради безопасности:

* **Общий материал.** Если материал стоит и на выбранном объекте, и на другом,
  его переподключают на всех пользователях. Если хоть один пользователь не
  может быть подготовлен, объект выпадает из переноса **целиком** вместе со
  своими материалами — иначе материал указал бы на слой, которого у объекта нет.
  Тест `part_shared` проверяет это.
* **Сбой не ломает экспорт.** Ошибка переноса записывается в отчёт, и экспорт
  идёт с исходными UV, как раньше.

---

## 25.7. Ограничения

* **Модификаторы, меняющие форму.** Координаты объекта берутся из базовой сетки.
  Если модификатор смещает вершины (Displace и т.п.), объектная проекция в
  экспорте может сдвинуться. Для таких случаев нужен бейк.
* **Топология.** Слой строится по петлям базовой сетки. Модификаторы, которые
  меняют число граней, при экспорте применяются заново; для обычных стен
  (без модификаторов) результат точный.
* **Экспорт использует только один UV-слой.** Все остальные UV-слои объекта
  временно убираются. Это осознанный выбор: FBX без него читает не тот слой.

---

## 25.8. Что проверить руками

1. Открыть `Walls.blend`, нажать **Экспорт в игру → FBX** на `WallDoor` и
   `WallWindow`.
2. В отчёте должно быть `Moved texture mapping into UVs: Wallpaper -> GAA_EXPORT`.
3. Открыть `.blend` снова: у `WallDoor` UV-слои — `UVMap`, материал `Wallpaper`
   подключён через `Mapping`, как и был.
4. Импортировать FBX в движок: у объекта один UV-слой, текстура ложится так же,
   как в Blender.

⚠️ **Отдельная находка.** В `Walls.blend` у материала `Wood_Dark_Bake` картинки
`WallDoor_albedo/normal/roughness` ссылаются на файлы, которых на диске сейчас
нет (папки `Wood_Dark_Bake` нет). Экспорт это честно пишет как `missing ... not
copying`. Поэтому дерево будет без текстуры, независимо от этой главы: сначала
нужно восстановить или перезапечь карты.
