# Глава 11. Скиллы: инструкции, которые модель запрашивает сама

> 📦 `src/blender_addon/skills.py`, `src/blender_addon/skills/*.md`,
> `state.py` (`_requested_skill`, `_fetch_skill`, `_prompt_with_skills`),
> `operators.py` (`_system_prompt`), `tests/skills_test.py`,
> `tests/run_skills_check.py`

## 11.1. Задача

Модель знает Blender «в среднем». Она путает имена сокетов (`Transmission`
вместо `Transmission Weight`), забывает про цветовое пространство текстур и
порядок нод. Спросить интернет она не может — она вообще ничего не может, кроме
как продолжить текст.

Значит, знания надо **принести в контекст**. Но просто «написать в системный
промпт всё, что мы знаем о материалах» не работает: промпт уезжает в модель при
*каждом* запросе, а контекстное окно конечно.

Идея: разбить знание на небольшие файлы и давать модели **каталог** (имя + одна
строка) всегда, а **тело инструкции** — только когда она его попросит.

## 11.2. Аналогия с MCP

В Model Context Protocol сервер отдаёт две вещи:

| MCP | У нас | Что это |
|---|---|---|
| *resource* | скилл (`skills/*.md`) | знание для чтения, ничего не исполняется |
| *tool* | рецепт (`materials.py`, оператор `gaa.pbr_from_folder`) | действие, которое исполняет аддон |

Скиллы — это «ресурсы». «Инструменты» у нас уже есть: кнопка «PBR из папки» не
генерируется моделью, а вызывается. Второе дешевле и надёжнее, но покрывает не
все случаи; первое гибче. Глава — про первое.

Настоящий MCP тут не нужен: он требует поддержки протокола у модели (tool
calling), которой у локальных Ollama-моделей может не быть вовсе. Мы делаем то
же самое **текстовым протоколом поверх обычного чата**.

## 11.3. Формат файла

```markdown
---
name: material-glass
title: Glass and transparent materials
description: Transmission Weight, IOR, roughness and the EEVEE settings
keywords: glass, transparent, transmission, ior, стекло, прозрачность
blender: ">=4.2"
---

# Рецепт
1. ...
2. ...

```python
mat = bpy.data.materials.new("Glass")
mat.use_nodes = True
...
```
```

Front matter — простой `ключ: значение`, разбирается вручную
(`parse_document`), без YAML-библиотеки: тянуть зависимость ради шести строк
незачем.

Поля:

- `name` — идентификатор, которым модель будет запрашивать скилл;
- `description` — **одна строка, которая всегда едет в промпт** в каталоге;
- `keywords` — задел на будущий поиск (сейчас не используется);
- `blender` — ограничение версии; файл с `>=4.2` не попадёт в каталог на 3.6.

Файл **без** `name` игнорируется — так рядом со скиллами может лежать обычный
README.

## 11.4. Каталог: что уходит в промпт всегда

`operators._system_prompt()` собирает промпт так:

```
системный промпт (prompts.py)
  + заголовок «Инструкции (skills)» + каталог   ← всегда
  + снимок сцены                                ← всегда (глава 7)
```

Каталог — это просто список строк из `skills.catalog()`:

```
- material-glass: Transmission Weight, IOR, roughness and the EEVEE settings
- material-principled: Exact Principled BSDF input names in Blender 4.x/5.x ...
```

Семь таких строк — около 600 символов. Тела инструкций (по 1.5–3 КБ каждое) в
промпт **не попадают**. Их приносят по запросу.

## 11.5. Протокол запроса

В заголовке каталога (`i18n`, ключ `prompt.skills_header`) модели сказано:
если нужна детальная инструкция — ответь ровно одним блоком

````
```skill
material-glass
```
````

и ничем больше. Терпимость к написанию: принимается и строка `SKILL: имя`, и
верхний регистр, и лишние пробелы — `parse_skill_requests()` в `skills.py`.

⚠️ Язык блока отличается от ```python: в `state.py` есть константа
`_CODE_LANGS = ("", "python", "py", "bpy")`, и `skill` в неё не входит. То есть
блок запроса инструкции никогда не попадёт в кнопку «Выполнить код». Плюс
`extract_last_code()` дополнительно отбрасывает пустой блок, содержащий ровно
имя скилла (на случай, если модель забыла поставить язык).

## 11.6. Второй проход: где он живёт и почему

Когда аддон видит `done` (модель закончила ответ), он делает так:

```
state._handle("done")
  ├── _requested_skill()   — есть ли в ответе запрос реального скилла?
  │      да  → _fetch_skill(name) → записать НОВУЮ команду chat и вернуться
  │      нет → _finish_reply()    — обычное завершение хода
  └── ...
```

`_fetch_skill()` не меняет историю. Он берёт **тот же** промпт, что и в первом
проходе, и приклеивает к нему тело инструкции:

```python
def _prompt_with_skills(self):
    if not self.skill_texts:
        return self.system_prompt
    parts = [self.system_prompt]
    for name, body in self.skill_texts:
        parts.append(f"# skill: {name}\n\n{body}")
    return "\n\n".join(parts)
```

и отправляет ту же самую переписку заново:

```python
self._write_command({
    "type": "chat",
    "config": self.last_config,
    "messages": build_messages(
        self.history, self._prompt_with_skills(), self.last_max_chars
    ),
})
```

Отсюда два следствия, которые стоит осознать:

1. **История не растёт.** В `self.history` нет ни промежуточного ответа модели
   («мне нужна инструкция»), ни тела инструкции. Модель получает
   обогащённый системный промпт и тот же самый вопрос. Так надёжнее: не
   приходится объяснять шаблону чата, что такое «сообщение-результат
   инструмента», а разные модели трактуют это по-разному.
2. **Воркер не менялся совсем.** Он по-прежнему «messages → chunks/done».
   Вся логика цикла — в аддоне, потому что аддон и так видит полный текст
   ответа (`stream_buf`) и владеет файлами скиллов. Воркеру не нужно ни
   читать файлы, ни знать про скиллы.

Почему это не бесконечно: `skills.MAX_SKILL_LOADS = 2`. Каждый проход — это
ещё один полноценный запрос к модели, так что бюджет маленький осознанно.
Кроме того, уже загруженные имена (`self.skill_texts`) не запрашиваются
повторно — если модель упрямо просит то же самое, ход просто завершается.

## 11.7. Что видит пользователь

Пока идёт подгрузка, пузырь ответа заменяется строкой
`msg.skill_loading` — «Читаю инструкцию: material-glass…». Промежуточный
ответ модели (который был бы мусором) стирается: `_fetch_skill()` делает
`self.stream_buf = ""`, а первый же `chunk` второго прохода перезапишет
пузырь финальным текстом.

Заодно поправлена старая шероховатость: в `_finish_reply()` текст ответа
прогоняется через `strip_skill_requests()` — на случай, если модель всё же
оставила блок запроса в финальном тексте, он не попадёт ни в историю, ни в
кнопку «Выполнить код». Пустой ответ теперь честно показывает
`(пустой ответ)` (раньше пузырь удалялся только когда он и так был пуст).

## 11.8. Бюджет контекста: почему `num_ctx`

Замер на стартовой сцене:

```
системный промпт RU      ~2100 символов
каталог скиллов           ~600 символов
снимок сцены              ~900 символов
итого                     ~3600 символов ≈ 1500–1800 токенов
```

Русский текст в BPE-разметке стоит примерно 2 символа на токен, английский —
около 4. Отсюда два решения:

- **тела скиллов написаны по-английски** — тот же скилл стоит вдвое дешевле, а
  Blender API модель знает по-английски лучше. Отвечает она всё равно на языке
  пользователя (это в системном промпте). Учебник `docs/` при этом остаётся
  русским: у него другой читатель — человек;
- **добавлена настройка `num_ctx`** (`preferences.py`, по умолчанию 16384).
  До этого `num_ctx` был жёстко 4096 в `asset_core/transport.py`, и один скилл
  на 2 КБ съедал бы треть всего окна. Значение уходит воркеру в `config`
  (`config_dict()`) и попадает в тело запроса Ollama как `"options":
  {"num_ctx": ...}`.

Хочешь увидеть суммарный размер своими глазами — запусти
`budget_measure`-подобный скрипт или просто напечатай `len(_system_prompt(bpy.context))`
в Text Editor.

## 11.9. Как это проверяется

Ключевое свойство: **скиллы — не проза, а проверяемые артефакты.** Два уровня.

**Быстрый (без Blender)** — `tests/skills_test.py`:

```
python -m pytest tests/skills_test.py -q
```

`skills.py` намеренно не импортирует `bpy`, поэтому тест грузит его по пути
через `importlib`. Проверяются: разбор front matter, фильтр версий, разбор
запроса, удаление блока запроса, что у каждого скилла есть описание и хотя бы
один ```python-блок.

**Главный (внутри Blender)** — `tests/run_skills_check.py`:

```
blender --background --factory-startup --python tests/run_skills_check.py
```

Он **исполняет каждый ```python-блок каждого скилла** на живом Blender и
падает, если хоть один бросил исключение. Именно это ловит переименование
сокета за секунды — тот самый баг «Стекло», который мы искали руками.
Третий раздел проверки, к тому же, прогоняет весь цикл второго прохода
синтетическими событиями (без модели): подсовывает `chunk`+`done` с блоком
`skill`, читает записанную команду и убеждается, что тело инструкции попало в
системный промпт, а ход остался `busy`.

Вот реальный вывод на Blender 5.2.2:

```
== library on Blender 5.2.2
   7 skills: material-colorspace, material-glass, material-metal-roughness, ...
ok   at least six skills are found
ok   request parsed
...
== executing code blocks (active object: 'Cube')
ok   material-glass block 1
ok   material-orm-packed block 2
...
== skill round trip (installed add-on)
ok   instruction appended to the system prompt
ok   turn stays busy while the instruction is fetched
RESULT: OK
```

## 11.10. Как добавить новый скилл

1. Создай `src/blender_addon/skills/materials/<имя>.md` с front matter; `name`
   должен быть уникальным, `description` — коротким (он виден всегда).
2. Напиши инструкции и добавь хотя бы один ```python-блок, который реально
   выполняется: только data API, без `bpy.ops` (в headless-проверке нет
   активного контекста), без чтения файлов с диска.
3. Запусти `tests/run_skills_check.py` (внутри Blender) и
   `tests/skills_test.py`. Если блок падает — правь скилл, а не тест.
4. Пересобери аддон: `python tools/build_addon.py`. Папка `skills/` уезжает в
   zip автоматически: `build_addon.py` копирует всё дерево
   `src/blender_addon` (`rglob`), а `asset_core` вендорится рядом.

Ни одна строка кода при этом не меняется — в этом и смысл: расширение знания
не требует расширения архитектуры.

## 11.11. Что попробовать руками

1. Спроси ассистента: «сделай стеклянный материал на выделенном кубе». В
   панели должна мелькнуть строка «Читаю инструкцию: material-glass…», а в
   ответе — `Transmission Weight`, а не `Transmission`.
2. Спроси про material, которого нет («сделай материал с подповерхностным
   рассеиванием по инструкции material-subsurface»). Каталог такого имени не
   содержит, поэтому второго прохода не будет — модель просто ответит как
   умеет. Это ожидаемое поведение: запрос несуществующего скилла не тратит
   запрос.
3. Открой `dist/asset_assistant-0.5.0.zip` и убедись, что внутри лежит
   `skills/` со всеми `.md` — иначе на чистой машине каталог будет пуст.

## 11.12. Автоподбор скилла по ключевым словам

Протокол запроса (раздел 11.5) работает, но только если **модель** его
использует. А инструкция может быть нужна и когда модель её не просит: человек
написал «сделай стеклянный материал» — рецепт стекла очевидно нужен, и тратить
на его запрос отдельный проход по модели обидно.

Поэтому есть **второй путь**: аддон сам смотрит, какие `keywords` скиллов
встретились в тексте пользователя, и прикрепляет нужное тело сразу, без второго
прохода.

📦 `skills.match(library, user_text)`:

```python
def match(skills, text, limit=MAX_AUTO_SKILLS, min_score=MIN_AUTO_SCORE):
    """Skills to attach to the prompt *without* a second round trip."""
    picked = []
    for score, skill in score_keywords(skills, text):
        if score < min_score:
            break
        picked.append(skill)
        if len(picked) >= limit:
            break
    return picked
```

### Как считается score

```python
for keyword in skill.keywords:
    if not _keyword_re(keyword).search(text):
        continue
    score += 1 if keyword.lower() in _WEAK_KEYWORDS else len(keyword)
```

Два решения:

1. **Границы слова.** Ключевое слово ищется как отдельное слово
   (`(?<!\w)ao(?!\w)`), а не подстрока. Иначе `ao` нашлось бы внутри «board», а
   `map` — внутри «mapping».
2. **Слабые слова ничего не решают сами.** Слова `texture`, `map`, `normal`,
   `material` есть почти в каждом вопросе про материалы. Если бы каждое давало
   полный балл, вопрос «настрой карту нормалей» подтянул бы сразу три инструкции.
   Для них вес — 1, а не длина слова.

Порог `MIN_AUTO_SCORE = 5` — это примерно одно «стекло» (6 букв) или одно
`chrome` (6). Слабых слов, набравших 5 баллов, не бывает.

### Где это вызывается

📦 `state.ChatState.send()` — до формирования сообщений:

```python
self.skill_texts = []
self.auto_skills = []
self._fetched_skills = 0

for skill in self._auto_skills(user_text):
    self.skill_texts.append((skill.name, skill.body))
    self.auto_skills.append(skill.name)

messages = build_messages(self.history, self._prompt_with_skills(), max_chars)
```

То есть авто-подключённые скиллы попадают в **тот же** системный промпт, что и
запрошенные моделью, — просто без затраты на лишний запрос.

⚠️ Авто-подключённые скиллы **не тратят** бюджет `MAX_SKILL_LOADS`: бюджет
считает только запросы модели (счётчик `_fetched_skills`), потому что авто-скилл
не стоил ни одного запроса.

### Как это выглядит

```
Пользователь: сделай прозрачный материал
В панели:     Читаю инструкцию: material-glass…
Модель:       (сразу получает тело рецепта стекла и отвечает)
```

Раньше в этом месте было бы два хода: «мне нужна инструкция» → рецепт →
ответ. Теперь — один.
