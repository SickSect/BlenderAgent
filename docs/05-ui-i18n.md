# Глава 5. Интерфейс и локализация

Здесь разбираем, как рисуется чат, почему один и тот же код показывается в четырёх
местах, как работает перенос строк по ширине окна и как устроены два языка
интерфейса.

## 5.1 Модель данных чата

Чат хранится в **RNA-свойствах** `WindowManager`. Из главы 1 мы помним, что
`PropertyGroup` — это структура, а `CollectionProperty` — список таких структур.
📦 `ui.py`:

```python
class GAAChatMessage(bpy.types.PropertyGroup):
    role: StringProperty(default="assistant")   # "user"|"assistant"|"error"|"result"
    body: StringProperty(default="")            # текст сообщения
```

При регистрации они привязываются к `WindowManager`:

```python
bpy.types.WindowManager.gaa_messages = CollectionProperty(type=GAAChatMessage)
bpy.types.WindowManager.gaa_active = IntProperty(default=0)
bpy.types.WindowManager.gaa_input = StringProperty(default="", ...)
```

Что это даёт:

- `wm.gaa_messages` — список сообщений; `.add()`, `.remove(i)`, `.clear()`;
- `wm.gaa_active` — индекс выделенной строки (его меняет `template_list`);
- `wm.gaa_input` — то, что набрано в поле ввода.

⚠️ `body` обрезается до `MAX_DISPLAY_CHARS = 8000` (📦 `state.add_display`): в
интерфейсе длиннющий ответ не нужен целиком, а хранить в RNA весь текст — лишняя
память. Полный текст всё равно уходит в историю для модели (она в Python, §3.4).

## 5.2 Список сообщений: `UIList`

Blender рисует прокручиваемые списки через `UIList`. Класс получает уже готовый
`layout` и **одну** строку `item`:

```python
class GAA_UL_messages(bpy.types.UIList):
    def draw_item(self, context, layout, data, item, icon,
                  active_data, active_propname, index):
        if self.layout_type in {"DEFAULT", "COMPACT"}:
            first_line = (item.body or "").splitlines()
            preview = first_line[0] if first_line else "..."
            if len(preview) > 70:
                preview = preview[:70] + "…"
            role_key = _ROLE_KEYS.get(item.role, "role.assistant")
            label = f"{i18n.T(role_key)}: {preview}"
            layout.label(text=label, icon=_ROLE_ICONS.get(item.role, "DOT"))
        elif self.layout_type == "GRID":
            layout.alignment = "CENTER"
            layout.label(text="", icon=_ROLE_ICONS.get(item.role, "DOT"))
```

Разберём аргументы `draw_item` — это интерфейс, который Blender навязывает:

| Аргумент | Что это |
|---|---|
| `self` | сам список (например, `self.layout_type`) |
| `context` | контекст Blender |
| `layout` | контейнер, куда рисовать **строку** |
| `data` | «владелец» списка (тут `WindowManager`) |
| `item` | **одно** сообщение (`GAAChatMessage`) |
| `icon` | предложенная иконка (можно игнорировать) |
| `active_data`, `active_propname` | где хранится индекс активной строки |
| `index` | номер этой строки в списке |

`layout_type` бывает `DEFAULT`, `COMPACT` (обычный список) и `GRID` (плитка). Мы
поддерживаем оба: в гриде рисуем только иконку.

Иконки: у пользователя — `USER`, у ассистента — `EVENT_A` («A» в кружке, ближайшее к
«AI»: иконки `BOT` в Blender нет), у ошибки — `ERROR`, у результата — `INFO`. Значения
ролей и иконок вынесены в словари `_ROLE_ICONS` / `_ROLE_KEYS`, чтобы не было
`if/elif`-лестниц.

⚠️ В `draw_item` **нельзя** обращаться к сети или тяжёлым вычислениям: он
вызывается на каждую видимую строку при каждой перерисовке.

## 5.3 Общая отрисовка: `draw_chat`

Вся компоновка живёт в одной функции 📦 `ui.py:draw_chat`, потому что её используют
**четыре** хоста (три панели + popup). Порядок отрисовки сверху вниз:

```python
def draw_chat(layout, context, *, show_window_button=True,
              wrap_width=_WRAP_WIDTH, title=False):
    wm = context.window_manager
    chat = state.get_state()
    prefs = preferences.get_prefs(context)
    ...
```

1. **Заголовок** — только в popup (`title=True`): у всплывающего окна нет родной
   полосы заголовка, поэтому рисуем сами.
2. **Статусная строка** — `busy` → «Генерация…», иначе ошибка / готов + имя модели /
   просто «Готов».
3. **История** — `template_list` + детальный блок для выбранного сообщения.
4. **Ошибка** — если есть и не `busy`, показываем отдельным блоком.
5. **Ожидающий код** — превью первых `_CODE_PREVIEW_LINES` строк и кнопки
   «Выполнить код» / «В Text Editor».
6. **Ввод и действия** — поле ввода, «Отправить»/«Стоп», «Очистить»/«Настройки»,
   при необходимости кнопка «Окно чата».

Ключевой фрагмент — история и подробности выбранного сообщения:

```python
layout.template_list("GAA_UL_messages", "", wm, "gaa_messages", wm, "gaa_active", rows=7)
active = wm.gaa_active
if 0 <= active < len(wm.gaa_messages):
    item = wm.gaa_messages[active]
    if item.body.strip():
        detail = layout.box()
        _draw_wrapped(detail, item.body, wrap_width)
```

`template_list` берёт: имя `UIList`-класса, имя списка (пустое), владельца данных
(`wm`), имя коллекции (`"gaa_messages"`), владельца активного индекса (`wm`), имя
индекса (`"gaa_active"`) и высоту в строках (`rows=7`). Почему строки — короткие
превью, а полный текст — в отдельном блоке? Потому что панель узкая, и простыня
текста в списке превращается в кашу.

Кнопка запуска кода учитывает `code_ran`:

```python
if chat.code_ran:
    row.label(text=i18n.T("pending.ran"), icon="CHECKMARK")   # уже выполнено
else:
    row.operator("gaa.run_code", icon="PLAY")                 # можно выполнить
row.operator("gaa.code_to_text", text="", icon="TEXT")
```

## 5.4 Перенос строк: почему вручную

В Blender UI `label` **не переносит** длинный текст по словам — он либо обрезается,
либо растягивает панель. Поэтому перенос делаем сами через стандартный `textwrap`
(📦 `ui.py:_draw_wrapped`):

```python
def _draw_wrapped(box, text, wrap_width=_WRAP_WIDTH):
    lines = []
    for paragraph in text.split("\n"):
        wrapped = textwrap.wrap(paragraph, width=wrap_width)
        lines.extend(wrapped if wrapped else [""])
    if len(lines) > _MAX_DETAIL_LINES:
        head = lines[: _MAX_DETAIL_LINES // 2]
        tail = lines[-(_MAX_DETAIL_LINES // 2):]
        lines = head + ["…"] + tail
    for line in lines:
        box.label(text=line if line else " ")
```

Две вещи:

- **Свой разбивкой по параграфам** (`text.split("\n")`) мы не даём `textwrap` «съесть»
  пустые строки — иначе абзацы склеятся.
- **Усечение с «…»** посередине: если строк больше `_MAX_DETAIL_LINES` (60), показываем
  начало и конец. Это защита от «гигантских» ответов, которые заморозили бы отрисовку.

⚠️ `box.label(text=line if line else " ")` — пустую строку заменяем на пробел, потому
что `label(text="")` в некоторых темах схлопывается и ломает ритм.

## 5.5 Четыре хоста: три панели и одно окно

Blender привязывает панель ровно к одной паре `(space_type, region_type)`. Значит,
чтобы чат был в трёх редакторах, нужны три класса. Но чтобы не дублировать код
отрисовки, используется **миксин** (`_GAAChatPanelMixin`) и один `draw_chat`:

```python
class _GAAChatPanelMixin:
    bl_label = "AI Assistant"
    bl_category = "AI"
    def draw(self, context):
        draw_chat(self.layout, context)

class GAA_PT_main(_GAAChatPanelMixin, bpy.types.Panel):
    bl_idname = "GAA_PT_main"
    bl_space_type = "VIEW_3D"       # 3D-вьюпорт (N → AI)
    bl_region_type = "UI"

class GAA_PT_shader(_GAAChatPanelMixin, bpy.types.Panel):
    bl_idname = "GAA_PT_shader"
    bl_space_type = "NODE_EDITOR"   # редактор шейдеров/нод
    bl_region_type = "UI"

class GAA_PT_image(_GAAChatPanelMixin, bpy.types.Panel):
    bl_idname = "GAA_PT_image"
    bl_space_type = "IMAGE_EDITOR"  # редактор изображений
    bl_region_type = "UI"
```

Это приём «**миксин + тонкие наследники**»: поведение один раз, привязка к месту —
отдельно. Ровно то, что нужно, когда один и тот же вид нужен в нескольких местах.

### Popup-окно (Ctrl+Alt+A)

Плавающее окно — это **оператор**, а не панель. Оператор открывает модальный popup с
нашим `draw` (📦 `operators.py:GAA_OT_chat_window`):

```python
def invoke(self, context, event):
    width = _chat_popup_width(context)          # из настроек
    self._wrap = ui.popup_wrap_width(width)     # символов в строке
    return context.window_manager.invoke_popup(self, width=width)

def execute(self, context):
    return self.invoke(context, None)           # вызов из F3/скрипта

def draw(self, context):
    ui.draw_chat(self.layout, context,
                 show_window_button=False,      # в popup эта кнопка лишняя
                 wrap_width=self._wrap or ui._WRAP_WIDTH,
                 title=True)
```

Две тонкости:

- `invoke` — интерактивный запуск (открыть окно); `execute` перенаправляет туда же,
  потому что `F3`-поиск и скрипты запускают оператор в EXEC-контексте без `invoke`.
- `show_window_button=False`, иначе внутри popup была бы кнопка «открыть popup».

## 5.6 Ширина и перенос: как одно число управляет всем

Пользователь задаёт **ширину окна в пикселях** (`chat_width`, 300–1400). А рисовать
надо **в символах**. Пересчёт (📦 `ui.py`):

```python
_POPUP_FONT_WIDTH = 7     # примерная ширина символа в px
_POPUP_PADDING = 90       # px на рамки/отступы

def popup_wrap_width(width_px: int) -> int:
    return max(30, (width_px - _POPUP_PADDING) // _POPUP_FONT_WIDTH)
```

Логика простая: от ширины окна отнимаем отступы, делим на ширину символа, получаем
приблизительное количество символов в строке; `max(30, ...)` — защита от слишком узкого
значения. Это **оценка**, а не точный расчёт: точную ширину шрифта Blender Python не
отдаёт. Зато при изменении `chat_width` перенос текста перестраивается сам — потому
что `wrap_width` передаётся в `draw_chat` параметром, а не зашит константой.

⚠️ Панели в боковых списках узкие фиксированно, поэтому у них `_WRAP_WIDTH = 54`
символа. У popup ширина своя, поэтому там работает расчёт.

## 5.7 Локализация: одна таблица строк и функция `T()`

Идея (📦 `i18n.py`): **ни одна строка интерфейса не зашита в код**. Все они лежат в
словаре под стабильными ключами:

```python
STRINGS = {
    "ru": {
        "chat.title": "AI Assistant — чат",
        "status.busy": "Генерация…",
        "op.send.label": "Отправить",
        "status.ready_model": "Готов · {model}",
        ...
    },
    "en": {
        "chat.title": "AI Assistant — chat",
        "status.busy": "Generating…",
        "op.send.label": "Send",
        "status.ready_model": "Ready · {model}",
        ...
    },
}
```

А код везде зовёт `T("ключ")`:

```python
def T(key: str, **fmt) -> str:
    lang = get_lang()
    text = STRINGS[lang].get(key)
    if text is None:
        text = STRINGS[DEFAULT_LANG].get(key, key)   # фолбэк
    return text.format(**fmt) if fmt else text
```

Три свойства, которые делают это надёжным:

1. **Каждый вызов `T()` читает текущий язык заново** (`get_lang()`), поэтому
   переключение языка применяется уже на следующей перерисовке — без перерегистрации
   панелей.
2. **Фолбэк при опечатке**: нет ключа → берём из языка по умолчанию → если и там нет,
   возвращаем **сам ключ**. Опечатка превращается в видимую странность (`status.busyy`),
   но не в падение.
3. **Подстановка значений** через `{}`: `T("status.ready_model", model="qwen2.5-coder:7b")`.

`get_lang()` терпеливо обёрнут в `try/except`:

```python
def get_lang() -> str:
    try:
        import bpy
        addon = bpy.context.preferences.addons.get(__package__)
        if addon is not None and addon.preferences is not None:
            lang = str(getattr(addon.preferences, "language", "")).lower()
            if lang in STRINGS:
                return lang
    except Exception:
        pass
    return DEFAULT_LANG
```

Почему так осторожно? Потому что `T()` может понадобиться **до** регистрации аддона
или в headless-режиме, где настроек нет. Тогда спокойно возвращается `"ru"`.

**Добавить язык** = добавить один словарь в `STRINGS` и один пункт в `EnumProperty`
`language`. Больше нигде ничего менять не нужно.

## 5.8 Сложный случай: «запечённые» строки RNA

Вот тут начинается самое интересное. Строки вроде `chat.title` мы рисуем сами и
можем менять когда угодно. Но есть строки, которые Blender **копирует в RNA при
регистрации класса**:

- `bl_label` оператора (надпись на кнопке),
- докстринг оператора (тултип),
- `name`/`description` у свойств,
- названия пунктов `EnumProperty`.

Это значит: если просто поменять язык, кнопка «Отправить» останется русской до
**перерегистрации** оператора. Так устроен RNA.

Решение — при смене языка перерегистрировать операторы (📦 `preferences.py`):

```python
def _on_language_update(self, _context):
    from . import operators      # локальный импорт: циклическая зависимость
    operators.refresh_labels()
```

А `refresh_labels()` (📦 `operators.py`) делает это **в два этапа**, потому что
`unregister_class` может упасть:

```python
def refresh_labels() -> None:
    removed = []
    for cls in reversed(_classes):
        try:
            bpy.utils.unregister_class(cls)
        except (RuntimeError, ReferenceError):
            # не смогли снять (например, «жив» экземпляр модального оператора:
            # открыт popup чата во время поиска F3) — возвращаем уже снятые назад
            for back in reversed(removed):
                bpy.utils.register_class(back)
            return
        removed.append(cls)
    _apply_labels()
    for cls in _classes:
        bpy.utils.register_class(cls)
```

Почему так сложно:

1. Сначала **снимаем все** классы, запоминая снятые.
2. Если какой-то снять не удалось (живёт экземпляр оператора) — **возвращаем всё
   снятое обратно** и выходим. Это транзакционность: аддон не остаётся «полуснятым».
3. Только когда снялись все — обновляем подписи (`_apply_labels`) и регистрируем заново.

`_apply_labels()`:

```python
def _apply_labels() -> None:
    for cls in _classes:
        cls.bl_label = _label_for(cls)       # из i18n по op.<id>.label
        # докстринг тоже обновляем → обновится и тултип
```

⚠️ Полностью победить «запечёнку» нельзя: описания некоторых **preferences**-свойств
остаются в исходном языке до полной перезагрузки аддона. Это задокументированное
ограничение (см. шапку `i18n.py` и README).

## 5.9 Перерисовка

Мы уже видели `_redraw()` в главе 3. Повторим главное: после изменения состояния нужно
попросить Blender перерисовать, иначе экран обновится «когда-нибудь».

```python
def _redraw() -> None:
    wm = _wm()
    for window in wm.windows:
        screen = window.screen
        for area in screen.areas:
            area.tag_redraw()
            for region in area.regions:
                region.tag_redraw()
```

И помним оптимизацию: `pump()` зовёт `_redraw()` **только если были события** (§3.7),
чтобы не перерисовывать интерфейс на каждом тике таймера.

## 5.10 Итог главы

- Состояние чата — RNA-свойства `WindowManager` (`gaa_messages`, `gaa_input`,
  `gaa_active`), модель данных — `GAAChatMessage` + `UIList`.
- Одна функция `draw_chat` обслуживает четыре хоста; привязка к месту — в тонких
  наследниках панелей и в popup-операторе.
- Перенос строк делаем вручную (`textwrap`), ширину popup переводим из px в символы
  приблизительным расчётом.
- i18n — таблица `STRINGS` + `T()` с фолбэком; язык читается на каждый вызов.
- «Запечённые» строки RNA требуют перерегистрации операторов, сделанной
  транзакционно (см. `refresh_labels`).

Глава 6 — то, ради чего всё это: материалы и текстуры.
