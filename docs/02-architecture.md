# Глава 2. Архитектура аддона

Глава 1 дала кирпичи. Здесь — чертёж здания: из каких модулей состоит аддон, кто
за что отвечает и как течёт информация.

## 2.1 Общая картина

Аддон делится на **две половины**, и это важнейшее архитектурное решение:

```
┌──────────────────────────────────────────────────────────────┐
│                      ВНУТРИ Blender                          │
│                                                              │
│  src/blender_addon/                                          │
│    __init__.py      register/unregister, хоткей Ctrl+Alt+A   │
│    preferences.py   настройки (язык, бэкенд, ширина чата)     │
│    ui.py            панели в 3 редакторах + popup-окно        │
│    operators.py     кнопки и выполнение AI-кода               │
│    state.py         состояние чата + мост к воркеру           │
│    snapshot.py      описание сцены для промпта                │
│    prompts.py       системные промпты RU/EN                   │
│    i18n.py          строки интерфейса RU/EN + T()             │
│                          │                                    │
│                          │  JSONL-файлы (commands/events)     │
│                          ▼                                    │
└──────────────────────────────────────────────────────────────┤
                                                               │
┌──────────────────────────────────────────────────────────────┘
│                    ОТДЕЛЬНЫЙ ПРОЦЕСС
│
│  src/asset_core/
│    worker.py        читает команды, пишет события
│    transport.py     HTTP к Ollama / OpenAI (только stdlib)
│
└─────────────── HTTP ───────────────────────► Ollama / внешний API
```

**Правило разделения:** `asset_core` **не импортирует `bpy`** — он ничего не знает
про Blender и собирается только из стандартной библиотеки (`json`, `urllib`,
`subprocess`). Вследствие этого:

- его можно тестировать и запускать без Blender;
- его можно переиспользовать в CLI-версии проекта (`src/codeagent`);
- его нельзя случайно «уронить» вызовом Blender-API из фонового процесса;
- при сборке расширения он «вендорится» внутрь zip, чтобы тот был самодостаточным
  (см. §2.6).

## 2.2 Карта модулей

| Модуль | Ответственность | Не знает про |
|---|---|---|
| `__init__.py` | регистрация всего, хоткей, реакция на загрузку файла | детали чата |
| `preferences.py` | настройки, `config_dict()` для воркера | UI, воркер |
| `i18n.py` | строки RU/EN, `T()` | всё остальное |
| `prompts.py` | системный промпт RU/EN | — |
| `snapshot.py` | текст-описание сцены | как он используется |
| `state.py` | история, запуск воркера, чтение JSONL, таймер | UI-компоновку |
| `ui.py` | отрисовка чата, панели, модель сообщения | сеть |
| `operators.py` | кнопки, `exec` AI-кода | HTTP |

Зависимости идут «в одну сторону»:

```
__init__ ──> preferences, ui, operators, state
operators ─> i18n, preferences, prompts, snapshot, state, ui
ui ────────> i18n, preferences, state
state ─────> i18n
asset_core.worker ─> asset_core.transport
```

Никаких циклов: `state.py` не знает про `ui.py`, а `ui.py` не знает про сеть.
Это делает код предсказуемым.

## 2.3 Три вида состояния

В аддоне три разных «хранилища» состояния, и их важно не путать:

| Где | Что лежит | Переживает перезагрузку .blend? |
|---|---|---|
| `bpy.context.window_manager` (RNA) | список сообщений `gaa_messages`, текст ввода `gaa_input`, выделенная строка `gaa_active` | **Нет** (обнуляется) |
| Синглтон `ChatState` (Python) | история для модели, `busy`, `pending_code`, ссылка на процесс воркера | Нет (живёт, пока запущен Blender) |
| `bpy.data` (данные сцены) | объекты, материалы, текстовые блоки — всё, что меняет AI-код | **Да** |

Почему `gaa_messages` в `WindowManager`, а не в Python-списке? Потому что RNA-свойства
можно рисовать и сохранять средствами самого Blender (`template_list`,
`layout.prop`), и они автоматически очищаются при загрузке нового файла.

Почему история для модели — в Python? Потому что она нужна только нашему коду, а
не интерфейсу, и её формат (список `{"role": ..., "content": ...}`) — это формат
запроса к LLM, а не отображения.

📦 Ирония: два состояния приходится **синхронизировать вручную**. Когда грузится
новый .blend, RNA-список очищается — и `__init__.py` в `load_post` вызывает
`reset_session()`, чтобы Python-история тоже очистилась. Иначе модель «помнила»
бы старую сцену.

## 2.4 Путь одного запроса (chat)

Проследим, что происходит, когда пользователь ввёл текст и нажал «Отправить»:

```
1. Кнопка "Send"  →  bpy.ops.gaa.send()
2. GAA_OT_send.execute(context):
     - берёт текст из context.window_manager.gaa_input
     - собирает системный промпт (prompts.system_prompt + snapshot.build_snapshot)
     - собирает config из prefs (preferences.config_dict)
     - вызывает ChatState.send(...)
3. ChatState.send:
     - запускает воркер, если его нет  (ensure_worker → subprocess.Popen)
     - добавляет сообщение в history и в экран (add_display)
     - пишет одну строку JSON в commands.jsonl
     - регистрирует таймер (ensure_timer)
4. Воркер (отдельный процесс):
     - читает новую строку из commands.jsonl
     - делает HTTP-запрос к Ollama/OpenAI (transport.stream_chat)
     - на каждый кусочек ответа пишет {"type":"chunk","text":"..."} в events.jsonl
     - по завершении пишет {"type":"done"}
5. Таймер (каждые 0.1 с) в главном потоке Blender:
     - ChatState.pump() читает новые строки из events.jsonl
     - _handle() складывает chunk'и в stream_buf и обновляет последний экранный элемент
     - по "done": дописывает ответ в history, извлекает код (extract_last_code)
     - _redraw() перерисовывает окна
6. Пользователь видит стриминг в чате и (если есть) блок кода с кнопкой "Run code".
```

Схема связей:

```
Blender add-on  --commands.jsonl-->  sidecar worker  --HTTP-->  Ollama / API
   (timers)       <--events.jsonl---  (own process)
```

Почему не проще «просто сделать HTTP-запрос из Blender»? Потому что запрос
занял бы секунды и заморозил интерфейс; а фоновый поток в Blender официально не
поддерживается. Подробности и код — глава 3.

## 2.5 Путь выполнения AI-кода

Второй поток данных — когда модель прислала код и пользователь нажал «Выполнить код»:

```
1. Ответ модели извлечён в ChatState.pending_code (последний ```python-блок)
2. bpy.ops.gaa.run_code()  (кнопка появляется, если pending_code не пуст)
3. GAA_OT_run_code.execute:
     - берёт код из chat.pending_code
     - _exec_script(...): подменяет контекст на 3D-вьюпорт (temp_override),
       выполняет exec(code), затем view_layer.update()
     - ловит исключения → пишет traceback в чат
     - ставит code_ran = True (повторный запуск того же блока запрещён)
4. Весь запуск — один шаг Undo (bl_options = {"REGISTER", "UNDO"})
```

Здесь нет сети и воркера — только `exec` в главном потоке. Но именно тут таится
самая опасная часть, поэтому ей посвящена целая глава 4.

## 2.6 Сборка и упаковка

Blender 4.2+ ставит аддоны как **расширения**: zip-архив с файлом
`blender_manifest.toml` (он заменил старый `bl_info` для механизма расширений).

Сборкой занимается 📦 `tools/build_addon.py`:

```
1. читает версию из src/blender_addon/blender_manifest.toml
2. копирует src/blender_addon/        во временную папку
3. копирует src/asset_core/  как  <temp>/asset_core/   ← «вендоринг»
4. пакует всё в dist/asset_assistant-<версия>.zip
5. проверяет архив: blender --command extension validate <zip>
```

Важные детали:

- В zip кладутся **два** дерева: сам аддон и вендоренный `asset_core`. Поэтому
  установленный аддон самодостаточен.
- Имя пакета (`PACKAGE_ID`) и версия берутся из манифеста — единственный источник
  правды о версии.
- Файловая структура внутри zip: `blender_manifest.toml` и `__init__.py` в корне.

📦 `state.py` умеет находить воркер в двух местах (`_worker_script`):
`<addon>/asset_core/worker.py` (установленное расширение) или
`<repo>/src/asset_core/worker.py` (запуск из исходников). Так один и тот же код
работает и при разработке, и после установки.

## 2.7 Жизненный цикл

```
Установка расширения
   │
Включение галочки в Preferences
   │   Blender импортирует модуль и вызывает register()
   ▼
register(): preferences → ui → operators → keymap → load_post handler
   │
Работа: кнопки, чат, воркер (запускается лениво при первом Send)
   │   Ctrl+Alt+A открывает popup; панели рисуются в 3 редакторах
   ▼
Выключение галочки / выход
   │
unregister(): снять load_post → убрать keymap → остановить таймер →
             убить воркер → снять операторы → панели → настройки
```

Порядок в `unregister()` обратный порядку `register()`. Это правило Blender:
если снимать классы раньше, чем ссылки на них, можно получить висячие указатели.

📦 `src/blender_addon/__init__.py`:

```python
def register():
    preferences.register()
    ui.register()
    operators.register()
    _register_keymap()
    bpy.app.handlers.load_post.append(_on_load_post)

def unregister():
    bpy.app.handlers.load_post.remove(_on_load_post)
    _unregister_keymap()
    state.remove_timer()
    state.get_state().kill_worker()
    operators.unregister()
    ui.unregister()
    preferences.unregister()
```

⚠️ `kill_worker()` в `unregister()` обязателен: иначе процесс воркера останется
висеть и будет держать файлы. Но одной этой строки мало на случай **краша**
Blender (тогда `unregister` не вызовется вовсе) — поэтому у воркера есть ещё и
собственный «сторож» (глава 6/§3).

## 2.8 Что менять, когда расширяешь

Шпаргалка «куда идти за правкой»:

| Задача | Файл |
|---|---|
| Новая настройка | `preferences.py` (+ ключ строки в `i18n.py`) |
| Новая кнопка/оператор | `operators.py` (+ строка `op.*` в `i18n.py`) |
| Изменить внешний вид чата | `ui.py` |
| Другая информация о сцене в промпте | `snapshot.py` |
| Строки/язык | `i18n.py` |
| Поведение запроса/истории | `state.py` |
| Другой бэкенд (провайдер) | `asset_core/transport.py` + `preferences.config_dict` |
| Логика воркера/протокол | `asset_core/worker.py` |

Следующая глава разбирает самый интересный механизм — общение с воркером.
