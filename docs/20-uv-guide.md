# Глава 20. Гайд по UV-картам: что это, зачем и как с этим работать

> 📦 Читатель, который в Blender не делал UV руками. Глава объясняет предметную
> область; план работ — в [`19-uv-roadmap.md`](19-uv-roadmap.md).
>
> ⚠️ В конце — словарик RU/EN и разбор «почему всё ломается».

---

## 20.1. Задача в одном абзаце

Твоя модель — это **треугольники в пространстве**. Текстура — это **плоская
картинка**. GPU не умеет «приложить картинку к поверхности» — ему нужно
сказать **точку за точкой**: вот эта вершина треугольника соответствует вот
этому пикселю картинки.

**UV-карта** — это и есть эта инструкция: для каждой вершины треугольника
хранится пара чисел `(u, v)` — где на картинке она лежит.

```
Модель (3D)                    Текстура (2D)
     ●─────────●                ┌──────────────┐
    /│        /│                │              │
   ●─────────● │      UV:       │  ●───────●   │
   │ │      │ │    (0.1,0.2) →  │  │       │   │
   │ ●──────│─●                │  ●───────●   │
   │/       │/                 └──────────────┘
   ●─────────●
```

⚠️ **Важное различие:** UV — это **не картинка**. Картинка (текстура) — это
цвета. UV — это **координаты**, которые говорит «цвет по этому месту».
Когда в Blender вы видите квадратную сетку в UV Editor — это и есть UV-карта
(пустая, без цветов). Тот же квадрат, залитый текстурой, — «текстура с UV».

## 20.2. Почему нельзя просто «приложить картинку»

Потому что поверхность **не плоская**, а картинка плоская. Пример — куб:

```
Вид сбоку:              Развёртка (вид сверху на UV):

    ┌────┐                    ┌──────────────┐
    │    │                    │   ┌────┐     │
    │    │                    │   │    │     │
    └────┘                    │   └────┘     │
  ┌──┴──┐                     │   ┌────┐     │
  │     │                     │   │    │     │
  └─────┘                     │   └────┘     │
                              └──────────────┘
```

Видите? Половина граней куба смотрит в другую сторону, чем видно сбоку. Чтобы
картинка не «смазалась» на гранях, которые мы не видим, поверхность надо
**разрезать** и **развернуть** на плоскость.

Это как карта мира на глобусе: сферу нельзя развернуть в плоскость без
разрывов — и глобус режут на куски. **Острова UV — это те же куски.**

⚠️ Отсюда сразу следует первое правило:

> **Развёртка всегда идёт с разрывами (швами).** Вопрос только в том, где их
> резать.

## 20.3. Что такое остров и шов

| Термин | Что это |
|---|---|
| **Остров** (island) | связная группа граней, развёрнутых вместе, без разрывов внутри |
| **Шов** (seam) | ребро, по которому поверхность разрезана; на нём UV «разрывается» |
| **Развёртка** (unwrap) | процесс превращения островов в UV-координаты |

Один куб после развёртки — это 6 островов (по грани) или 1 остров (если резать
по рёбрам, скрытым от камеры).

```
Куб с развёрткой «по граням» (6 островов):

  ┌───┐ ┌───┐ ┌───┐
  │   │ │   │ │   │
  └───┘ └───┘ └───┘
  ┌───┐ ┌───┐ ┌───┐
  │   │ │   │ │   │
  └───┘ └───┘ └───┘
```

## 20.4. Тексель и плотность текселей — самое важное понятие

**Тексель** = один пиксель текстуры.

**Плотность текселей** (texel density) = сколько текселей приходится на
единицу поверхности. Обычно измеряют в **пикселях на метр**.

### Пример

Текстура 1024×1024 налетает на куб со стороной 1 метр. Один остров (грань)
занимает в UV половину ширины → 512 пикселей на метр.

Тот же куб, но в сцене уменьшен до 0.5 метра → та же картинка, но теперь на
0.5 метра → **1024 пикселя на метр**. Текстура стала вдвое «жильнее» на
единицу площади.

```
Куб 1 м,  512 px/м  →  картинка «мягкая», детали теряются
Куб 0.5 м, 1024 px/м →  картинка «резкая», всё видно
```

### Почему это ломает работу

Если в сцене стоят два объекта с **разной плотностью**, одна и та же текстура
на них выглядит **по-разному**: на большом — мыльно, на маленьком — в шум.
Художник не может это объяснить и не может это исправить «на глаз»: он не
видит плотность в интерфейсе Blender вообще.

⚠️ **Вот почему плотность — критерий №1 в роадмапе.** Это единственная
проблема UV, которая **не видна** в редакторе, но **видна** в игре.

### Как считать

```
плотность = sqrt( (площадь_острова_в_UV × пиксели_текстуры) / площадь_острова_в_мире )
```

Площадь в UV берётся в **долях картинки** (0..1), площадь в мире — в
**квадратных метрах**. Результат — пиксели на метр.

## 20.5. Атлас: все острова в одной картинке

**Атлас** — это одна текстура, в которую уложены острова **разных** объектов
(иногда одного).

```
┌────────────────────────────────────┐
│  ┌────┐        ┌──┐                │
│  │    │        │  │    ┌──────┐     │
│  │    │        └──┘    │      │     │
│  └────┘                └──────┘     │
│       ┌────┐                        │
│       │    │      ┌──┐               │
│       │    │      │  │               │
│       └────┘      └──┘               │
└────────────────────────────────────┘
```

### Зачем атлас

| Причина | Пояснение |
|---|---|
| **Экономия памяти** | 10 текстур 512×512 = 10 МБ, один атлас 2048×2048 = 16 МБ... но одна текстура 4096×4096 = 64 МБ и **один** материал вместо десяти |
| **Один материал → один draw call** | на мобильных это разница между 30 fps и 60 |
| **Проще управлять** | один файл текстуры вместо папки |

### Проблема атласа: перекрытия

Если два острова наложились, они «смешиваются» — видна каша из двух текстур.
Поэтому острова **укладывают** с зазором.

## 20.6. Паддинг и мипмапы — почему края «замылены»

**Мипмап** — уменьшенная копия текстуры (512, 256, 128… до 1×1). GPU берёт
подходящую мипмап по расстоянию, чтобы дальние объекты не «мерцали».

Проблема: при уменьшении пиксели усредняются, и на **границе** острова в
усреднение попадают пиксели **соседнего** острова. На игровом объекте это
выглядит как тёмный или цветной **шлейф** по краю.

```
Без паддинга:        С паддингом:

  ▓▓▓▓  ▓▓▓▓           ▓▓▓▓  ▓▓▓▓
  ▓▓▓▓  ▓▓▓▓           ▓▓▓▓░▓▓▓▓
  ↑ мипмап усреднил    ↑ между островами пустая
    края двух островов    полоса — усреднять нечего
```

**Паддинг** — раздуть UV-острова на N пикселей, чтобы между ними была
«пустая» полоса. Именно поэтому в атласе между островами должно быть
**4–16 пикселей** зазора.

⚠️ В Blender 5.x оператор `uv.offset` (который это делал) **удалён**. Значит,
паддинг придётся реализовывать самим — на bmesh.

## 20.7. Что ещё ломается

| Симптом | Причина | Как проверить |
|---|---|---|
| Текстура «мылится» на одном объекте, чёткая на другом | разная плотность текселей | посчитать px/м для каждого |
| Цветные пятна, каша из двух текстур | острова перекрываются | `UV → Select → Overlap` |
| Чёрные или зеркальные края | UV выходят за пределы [0,1] | `UV → Select → Outside` (в 5.x оператора нет — считаем сами) |
| Шлейф по краям в игре | нет паддинга | смотреть на мипмап в Image Editor |
| Текстура «едет» при движении камеры | UV не закреплены / не пинованные | — |
| Швы видны как линии | швы проходят по видимым граням | швы должны идти по изломам и скрытым рёбрам |

## 20.8. Два режима: атлас и непрерывная развёртка

Ты хочешь, чтобы инструмент умел и то, и другое. И это правильно — **ядро
у них общее**, различается только последний шаг.

| | **Режим A: атлас** (игры) | **Режим B: непрерывная развёртка** (архвиз, 3D-печать, запекание) |
|---|---|---|
| Что на выходе | одна текстура со всеми островами | UV-развёртка, где каждый остров на своём месте, **без** укладки в общую картинку |
| Зачем | экономия памяти, один материал | карта «раскраски» по модели, запекание, 3D-печать |
| Плотность | **общая на весь атлас** | **своя у каждого острова** (часто — 1:1, «не искажать») |
| Перекрытия | недопустимы | недопустимы |
| Паддинг | **нужен** (мипмапы) | не нужен (нет атласа) |
| Укладка (`pack_islands`) | **да** | **нет** — острова остаются как есть |

### Что общее (это и есть «постепенно»)

```
                 ┌─────────────────────────────┐
                 │  ЯДРО (одинаково для обоих)  │
                 │                             │
                 │  U1 анализ: острова, плот- │
                 │     ность, перекрытия, выход │
                 │     за [0,1], искажение      │
                 │                             │
                 │  U2 швы + развёртка          │
                 │                             │
                 │  U3 плотность               │
                 └──────────────┬──────────────┘
                                │
             ┌──────────────────┴──────────────────┐
             │                                     │
     ┌───────▼────────┐                   ┌────────▼───────┐
     │  РЕЖИМ A: атлас │                   │ РЕЖИМ B: своё  │
     │  укладка +      │                   │ без укладки,   │
     │  паддинг +      │                   │ 1:1, для       │
     │  атлас-картинка  │                   │ запекания      │
     └─────────────────┘                   └────────────────┘
```

То есть U1–U3 делаются **один раз** и работают на оба режима. На режим B
тратится дополнительно один шаг — и всё.

⚠️ **Побочная выгода:** режим B — это, по сути, «развернуть и не трогать».
Тот же инструмент, только без укладки.

## 20.9. Как ручной шов отличается от автоматического

Авто-швы по углу — это **потолок** возможностей. На персонаже, одежде и
механизмах нужно резать поверхность **там, где скажет художник**, а шов
должен идти **скрытым** (под воротником, по внутренней стороне руки) —
тогда развёртка получается аккуратной, а остров — ровным.

Аддон умеет три вещи:

| Что | Как |
|---|---|
| **Развернуть только по своим швам** | галочка «Только по своим швам» в панели AI: автоматические швы **не ставятся** вообще |
| **Не затирать ручные швы** | автоматические швы **только добавляются** — если вы отметили шов вручную, он останется |
| **Разрезать по высоте** | «Разрез по высоте 1.2» — меш реально разрезается на этой высоте (как `Ctrl+R`), и новые рёбра становятся швами. Так делают рукава, сапоги и пояса |

⚠️ **Про разрез по высоте.** Чтобы разрезать, нужно **пересечь** вертикальные
рёбра, а не найти горизонтальные (на кубе горизонтальных рёбер посередине
нет). Поэтому разрез делается настоящим разрезом меша, а не поиском рёбер.
Высота считается в **мировых** координатах — работает и для сдвинутого
объекта.

⚠️ Доктор предупредит, если у модели **вообще нет швов**: замкнутая модель
развернётся одним куском, и текстурировать её будет нечем.

## 20.10. Симметричная развёртка: текстура вдвое меньше

**Идея:** развернуть только **половину** модели, а второй половине отдать те же
UV. Тогда текстура обслуживает обе стороны, а рисовать надо **вдвое меньше** —
эффективное разрешение удваивается.

⚠️ **Цена:** две половины лежат в UV **друг на друге**. Это перекрытие **по
замыслу**, и такой объект **нельзя класть в атлас** — у него своя текстура.

### Как это делается

```
1. швы по плоскости симметрии   → модель делится на две половины
2. развёртка
3. UV второй половины копируются у соответствующих вершин
```

### Если модель с модификатором Mirror

Тогда базовая сетка — уже половина, и модификатор сам достраивает вторую.
Аддон только **выключает «Mirror UVs»** у модификатора: с этой опцией
текстура была бы **не** зеркальной, а обычной.

### Соответствие вершин

У вершины и её зеркала одинаковое расстояние до плоскости симметрии — по
этому соответствие и находится. А вот **соответствие углов грани** ищется **по
вершине, а не по порядку**: у зеркальной грани обратный порядок обхода.

⚠️ Плоскость задаётся в **мировых** координатах (художник мыслит в мире), а
меш живёт в локальных. Плоскость переводится обратной матрицей — поэтому
работает и с повёрнутым объектом.

## 20.11. Как посмотреть UV в Blender руками

1. **Tab** — режим редактирования меша.
2. Вкладка **UV Editing** сверху (или `Shift+Tab` для переключения области).
3. Слева (или справа) — **UV Editor**, в нём сетка островов.
4. В **Image Editor** рядом — текстура; она ложится на сетку автоматически.
5. Проверить перекрытия: **UV → Select → Overlap** (в 5.2 есть).
6. Проверить плотность вручную: в UV Editor включить **View → Statistics** —
   показывает площадь и периметр выделения, но **не** плотность в px/м
   (её и считает наш инструмент).

⚠️ **Шаблонная развёртка (symmetric UV)** — отдельная техника для
симметричных объектов: одна сторона разворачивается, вторая — зеркально, и
модель рисуется **вдвое** меньше текстуры. Имеет смысл, когда рисуешь
вручную в Krita.

## 20.12. Круговорот с Krita и Aseprite — как это работает

Идея: сделать UV в Blender, **забрать карту** в графический редактор,
дорисовать текстуру, **вернуть** обратно.

### Почему это безопасно

Ключевое свойство:

> **Пока UV не менялись, раскладка и текстура всегда совпадают.**

Текстура — это картинка тех же пропорций, что и раскладка (2048×2048). Если
рисовать прямо по раскладке, каждый пиксель попадает на своё место. Поэтому
круговорот **не требует** ничего, кроме аккуратности в пикселях.

### Три шага

```
1. Blender: развернуть → уложить → экспортировать «комплект»
      uv_kit/
        layout.png            ← раскладка (где что лежит)
        manifest.json         ← размер, зазор, плотность, карты
        albedo_Crate.png      ← текущая текстура

2. Внешняя программа:
      Aseprite: открыть layout.png как направляющий слой,
                 нарисовать атлас поверх, сохранить как PNG
      Krita:    то же; есть фильтр «UV Map» для проверки

3. Blender: «Импортировать атлас» → PNG становится Base Color материала.
   UV не менялись → атлас совпадает по построению.
```

> 💡 **Почему это безопасно.** Импорт **не трогает UV**. Пока координаты не
> менялись, раскладка и текстура совпадают всегда. Поэтому круговорот не
> требует ничего, кроме аккуратности в пикселях.

### Как открыть сразу в нужной программе

В Blender есть **Preferences → File Paths → Image Editor** — команда внешнего
редактора. Прописать туда Aseprite или Krita — и кнопка
**Image → External Edit** (в Image Editor) откроет картинку в ней. Наш аддон
сможет вызывать это одной кнопкой.

## 20.13. Что сделает аддон (коротко)

| Возможность | Что даёт |
|---|---|
| **Проверить UV** | плотность по каждому объекту, перекрытия, выход за границы, искажение — то, что не видно в редакторе |
| **Развернуть** | одна кнопка: швы по углу → развёртка → минимизация искажений → укладка |
| **Швы по углу** | настраиваемый порог: меньше угол → больше швов → точнее, но больше островов |
| **Плотность** | приводит все острова объекта к одной плотности в px/м — текстура одинаково резкая везде *(этап U3)* |
| **Атлас** | общий атлас из островов **нескольких объектов**: укладка с зазором, паддинг, единая плотность *(этап U4a)* |
| **Собрать атлас** | создаёт пустую атлас-картинку нужного размера под покраску *(этап U4a)* |
| **Режим B** (без атласа) | та же развёртка, но без укладки — для запекания и 3D-печати *(этап U4b)* |
| **Экспорт UV-комплекта** | раскладка + текстуры + манифест для внешней программы *(этап U5)* |
| **Импортировать атлас** | вернуть нарисованную картинку в материал *(этап U5)* |

### Как выравнивается плотность (и почему это непросто)

Плотность — **относительная** величина: упаковщик Blender масштабирует все
острова одним коэффициентом, чтобы они влезли в текстуру. Он сохраняет
**отношения** плотностей, но меняет абсолютное значение. Поэтому порядок
операций такой:

```
1. измерить плотность каждого острова — КАК ЕСТЬ, раскладку не трогая
2. домножить UV каждого острова на (цель / его плотность)
3. уложить острова — НЕ масштабируя и НЕ вращая
4. если острова перестали влезать в [0,1] — ужать их все одним коэффициентом
```

⚠️ Первый и третий шаги — ключевые, и оба were неправильными раньше.

**Шаг 1: мерить до укладки.** Плотность острова зависит только от его
собственной площади, а не от того, где он лежит. Если сначала уложить острова
(упаковщик их покрутит и отмасштабирует), то измеряешь уже **другую**
раскладку — и коэффициенты считаются от неверной базы. Хуже: укладка до
измерения **перерисовывает раскладку целиком** — именно это и было
«слетает развёртка».

**Шаг 3: укладывать без масштаба.** Обычная укладка растягивает острова по
всей текстуре — и **уничтожает** правку шага 2: плотность возвращается к
той, что была. С укладкой без масштабирования упаковщик только двигает
острова, и плотность остаётся там, куда её поставили.

**Понятная аналогия:** представь, что на столе уже лежат листы бумаги разного
размера и ты хочешь, чтобы на **всех** было одинаковое количество текста.
Сначала смотришь, сколько текста на каждом (шаг 1), уменьшаешь или
увеличиваешь текст (шаг 2) и **не перекладываешь** листы заново (шаг 3) —
потому что перекладывание всё бы перемешало.

Если плотность уже одинаковая, кнопка **не трогает UV вообще** — ни одного
сдвига. Раскладка меняется только когда есть что выравнивать, и всегда
отменяется одним `Ctrl+Z`.

### Как собирается общий атлас

Атлас — это **одна** текстура на **несколько** объектов. Упаковщик Blender
умеет укладывать острова только внутри одного объекта, поэтому раскладка
делается здесь:

```
1. измерить остров каждого объекта
2. привести его к целевой плотности → UV-размер острова становится известен
3. уложить прямоугольники в атлас
4. записать координаты обратно в UV-слой каждого объекта
5. раздуть острова (паддинг)
```

⚠️ **Шаг 2 — то, что связывает атлас с плотностью.** Размер острова в атласе
определяется мировым размером и плотностью:
`размер = d · √(мировая площадь) / √(пиксели)`. Поэтому у всех объектов в
атласе одинаковая плотность **автоматически** — и атлас не может оказаться
«слишком плотным»: если места не хватает, инструмент говорит, какой размер
текстуры нужен.

### Как управлять развёрткой

Три уровня, от простого к тонкому:

1. **Настройки проекта** — угол швов, метод, зазор, плотность, размер атласа.
   Живут **в сцене** (у гейм-проекта и архвиз-проекта они разные).
2. **Переопределение на вызов** — «разверни с углами 25°» для одной задачи.
3. **Ассистент видит текущие настройки** — они в снимке сцены, поэтому модель
   не выдумывает числа.

## 20.15. Запекание: мост из Blender в игру

**Запекание** (bake) — это рендер материала в картинку. Нужно оно потому, что
игровой движок **не умеет считать шум и градиенты**: он знает только
картинки.

```
процедурный материал  →  запекание  →  текстура  →  игра
```

### Что для этого нужно

| Требование | Что будет, если его нет |
|---|---|
| **Движок Cycles** | EEVEE не умеет запекать вообще |
| **UV без перекрытий** | острова запекутся друг в друга |
| **Изображение-таргет** | некуда писать результат |
| **Узел-таргет: активный И выделенный** | «No active and selected image texture node found» |
| **Цветовое пространство и float buffer** | карта нормалей сохранится как цвет → мусор |

### Почему «карта нормалей — это данные»

У запечённой карты нормалей **нет цвета** — в ней векторы. Поэтому:
`colorspace = Non-Color` и **float buffer** (float32). Если сохранить её как
обычную sRGB-картинку, нормали разъедутся при смене цветового пространства.

Карта albedo — наоборот, это цвет: `sRGB`, без float buffer.

### ⚠️ Три ловушки, на которые уходит время

1. **`other is node` — всегда False** для структур bpy: каждый доступ к
   структуре выдаёт **новую обёртку** Python. Узел надо искать через `==`
   (сравнивает указатели). Иначе узел-таргет не выделяется — и запекание
   молча отменяется.
2. **Сообщение об ошибке вводит в заблуждение.** «No active and selected image
   texture node found in material» звучит как «в материале нет узла-текстуры»,
   а на самом деле узел есть — просто **не выделен**.
3. **Другой меша в той же точке съедает лучи.** Если рядом стоит кубик из
   стартовой сцены, запечённого объекта не видно: лучи упираются в чужой
   объект.

### Как это делает аддон

Кнопка **«Запечь»** (или инструмент `bake.maps`):

```
1. проверить готовность: UV, перекрытия, материал, источник высоты
2. создать картинки-таргеты (правильного размера, пространства и буфера)
3. создать узлы-таргеты и сделать их активными и выделенными
4. переключить движок на Cycles
5. запечь
6. убрать временные узлы — в материале не остаётся мусора
7. вернуть движок и число сэмплов как было
```

⚠️ Запекание занимает **главный поток**: на большой сцене Blender «зависнет»
на минуты. Это нормально.

## 20.16. Карта нормалей из карты высот

**Карта высот** говорит «насколько высоко каждая точка». **Карта нормалей**
говорит «куда смотрит поверхность». Игровой движок не умеет считать высоты —
он читает только нормали.

### Как это работает

Карта нормалей — это **производная** карты высот. Для каждого пикселя смотрим
на высоту слева и справа (и сверху, снизу) — разница говорит о наклоне:

```
n = normalize( (-dh/du * strength, -dh/dv * strength, 1) )
rgb = n * 0.5 + 0.5
```

Ровно то, что делают xNormal и Substance — только не выходя из Blender.

⚠️ **Два решения, которые стоит знать:**

1. **Производная берётся на единицу UV, а не на пиксель.** Иначе результат
   зависит от разрешения карты высот: одна и та же лепка, выгруженная в 2K и
   в 4K, дала бы разный рельеф. Теперь — одинаковый (только деталей больше).
2. **Зелёный канал — по конвенции OpenGL** (+Y вверх), как у нормалей Blender
   и большинства игровых движков. Для DirectX есть переключатель.

### Это карта данных

Результат — `Non-Color` и **float buffer**. Сохранённая как обычная sRGB-картинка,
карта нормалей теряет смысл при смене цветового пространства.

### Аналогия

Представь рельеф на бумаге. Ты смотришь на него с высоты и видишь, что слева
возвышается. Карта нормалей — это схема, где в каждой точке нарисована стрелка
«в какую сторону смотрит поверхность». Плоская бумага → все стрелки вверх:
(0.5, 0.5, 1.0).

## 20.17. Итог главы

- UV — это **инструкция**, какой пиксель какой вершине соответствует. Без неё
  текстурировать нечем.
- Поверхность не плоская, поэтому её **режут на острова** — и резать надо по
  изломам, а не как попало.
- **Плотность текселей** (px/м) — единственный критерий UV, который не виден
  в редакторе и виден в игре. Ей и посвящён отдельный этап.
- **Атлас** экономит память и draw call'ы, но требует укладки без перекрытий и
  **паддинга** (иначе мипмапы тянут соседние острова в края).
- Два режима (атлас и непрерывная развёртка) делят **ядро**: анализ, швы,
  развёртка, плотность. Различается только финальная укладка — поэтому
  «сделать и для игр, и для всего остального» — это не вдвое дороже, а
  примерно на один шаг дороже.
- Круговорот с Krita/Aseprite безопасен, потому что **пока UV не менялись,
  раскладка и текстура совпадают всегда**.
- **Запекание** переводит процедурный материал в текстуры, которые понимает
  игровой движок; его главная сложность — не рендер, а **подготовка** (движок,
  UV, картинки-таргеты, узел-таргет).
